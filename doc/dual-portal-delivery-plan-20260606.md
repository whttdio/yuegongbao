# 粤工保 / 安责保双前端研发批次与验收任务书（当前仓库版）

日期：2026-06-06

## 1. 目标

把当前仓库从“已具备双门户骨架，但部分页面仍停留在基础 CRUD 或半包装态”推进到可长期维护的双前端体系：

- 一套后台
- 两个门户
- 一套权限底座
- 双工作台体验

本任务书直接面向研发排期、测试验收和后续派工。

## 2. 当前基础与判断

当前仓库已具备以下可复用能力：

- 双登录入口
  - `/login/ygb`
  - `/login/azb`
- 双构建命令
  - `build:ygb`
  - `build:azb`
- 门户配置与运行时切换
  - `src/config/portal.js`
  - `src/utils/portal.js`
- 门户鉴权与菜单过滤
  - `X-Portal-Code`
  - `allowedPortalCodes`
  - `defaultPortalCode`
  - `sys_menu.portal_scope`
- 页面目录已经拆分
  - `src/views/ygb`
  - `src/views/azb`

因此后续批次不再做“门户骨架搭建”，而是进入“模块深化与体验成型”阶段。

## 3. 实施总原则

1. 不拆后台库，不拆接口主链
2. 不复制业务表，不复制同名 controller
3. 先固化角色、菜单、门户边界，再深化页面体验
4. 先做高频模块工作台，再做低频详情页美化
5. 先让用户进入页面就知道先干什么，再谈功能堆叠

## 4. 批次拆分

## 批次 A：门户底座固化

### 目标

把双门户的入口、权限、菜单、默认归口彻底定死，避免后续页面反复返工。

### 输入

- 登录页差异
- 门户切换规则
- 角色默认门户
- 菜单 `portal_scope`

### 输出

- 门户配置固定
- 角色 `allowedPortalScope` 与 `defaultPortalCode` 生效
- 菜单按门户过滤
- 同账号进入不同门户时菜单与首页完全切换

### 验收

- 企业管理员登录默认进入 `ygb`
- 应急监管员登录默认进入 `azb`
- `ygb_insurer` 与 `ygb_bank` 进入 `ygb` 时自动回切 `azb`
- 菜单管理页可维护 `portal_scope`
- 角色授权页可按门户切换授权树

### 当前状态

- 已有基础，后续只做增量维护

## 批次 B：`ygb` 主业务门户深化

### 目标

把 `ygb` 从“后台菜单集合”升级为企业管理员、经办、财务、人社监管的高频工作台。

### 优先模块

- `home`
- `cockpit`
- `contract`
- `attendanceRaw`
- `attendanceMonthly`
- `salaryBatch`
- `salaryDetail`
- `socialPayment`
- `socialBaseCompare`
- `taxCompare`
- `employmentRatio`
- `fakeOutsourcing`
- `newformWorker`
- `occupationMonitor`
- `statReport`

### 每个模块必须补齐的能力

- 摘要卡
- 焦点队列
- 当前对象动作区
- 角色提示
- 详情页重点
- 推荐联动模块

### 验收

- 企业管理员进入页面先看到“待办和堵点”，不是先看到表格
- 经办进入页面先看到“新增、导入、回写、结束”
- 财务进入页面先看到“对账、补缴、差异、发薪”
- 人社监管进入页面先看到“区域对象、异常企业、月报闭环”

## 批次 C：`azb` 主治理门户深化

### 目标

把 `azb` 做成应急监管、保险机构、银行协同可长期使用的治理工作台，而不是 `ygb` 的换皮页。

### 优先模块

- `home`
- `cockpit`
- `warning`
- `warningRule`
- `device`
- `aqInsurance`
- `heightWorkReport`
- `aiReport`
- `aiReportConfig`
- `creditScore`
- `statReport`
- `preventionFund`
- `preventionProject`
- `injuryEvent`
- `enterprise`
- `person`
- `uninsuredList`

### 每个模块必须补齐的能力

- 治理摘要卡
- 风险队列
- 当前对象动作面板
- 时效标签
- 角色轻视图
- 区域治理入口

### 验收

- 应急监管员先看到高风险对象和处置路径
- 保险机构只保留只读摘要、详情、报表、导出
- 银行协同只保留工资风险、信用结果、报表摘要
- 设备、高处作业、安责险页面不再停留在普通 CRUD 视角

## 批次 D：双视图共底座模块成型

### 目标

对共底座模块统一“后台单源、前端双视图”的模式，避免一会儿共页、一会儿拆页。

### 模块范围

- `enterprise`
- `person`
- `warning`
- `warningRule`
- `device`
- `aqInsurance`
- `preventionFund`
- `preventionProject`
- `injuryEvent`
- `heightWorkReport`
- `aiReport`
- `aiReportConfig`
- `creditScore`
- `statReport`
- `uninsuredList`

### 输出要求

- 共享 API / DTO / 列表查询 / 详情接口
- `ygb` 页面强调办理与闭环
- `azb` 页面强调治理与时效
- 只读角色统一收口

### 验收

- 同一条数据在两个门户都能看到
- 两边摘要、默认动作、详情重点不同
- 两边都不新增第二套业务表和第二套主接口

## 批次 E：评分体系与业务口径挂接

### 目标

把 530.1 与 6.1 从“并列文档”变成“同底数、双解释”的系统能力。

### 输出

- `ygb` 解释口径围绕业务办理链
- `azb` 解释口径围绕治理成效链
- AI 报告、信用评价、统计报表可按门户输出不同摘要

### 验收

- 同一企业在 `ygb` 与 `azb` 首页摘要不同
- 同一评分结果在两个门户的解释顺序不同
- 评分权重与目标值仍走配置，不写死在页面

## 批次 F：体验收口与验收联调

### 目标

补齐高频用户体验缺口，形成可持续维护的双门户体系。

### 必做事项

- 列表默认排序按焦点优先级重排
- 详情抽屉带“当前建议动作”
- 角色轻视图统一
- 门户间跳转不丢当前上下文
- 首页、驾驶舱、模块工作台分工彻底拆开

### 验收

- 高频角色进入页面 10 秒内能判断“先做什么”
- 不再需要在左侧菜单来回找模块
- 企业、监管、保险、银行的页面首屏关注点明确不同

## 5. 研发派工建议

建议按下面的开发顺序排：

1. 先做权限与门户边界稳定
2. 再做 `ygb` 高频办理链
3. 再做 `azb` 高频治理链
4. 再补双视图共底座模块
5. 最后统一评分解释、报表口径和体验收口

建议按团队分工：

- A 组：后端权限 / 菜单 / 角色 / 门户边界
- B 组：`ygb` 企业办理链页面
- C 组：`azb` 治理链页面
- D 组：共享摘要接口 / 报表 / 评分解释
- E 组：联调、验收、回归

## 6. 每批统一验收清单

每一批都按同一口径验收：

1. 是否仍保持单后台、单业务表、单主接口
2. 是否真的做出双门户差异，而不是简单换标题
3. 是否有角色视角差异，而不是所有人同一个页面
4. 是否把首屏从“表格浏览”升级为“工作台动作”
5. 是否可以分别通过 `build:ygb` 与 `build:azb`

## 7. 最终交付判断标准

最终不是看“两个前端目录有没有”，而是看下面四件事是否真正成立：

1. 同一套后台是否已经承接两套监管语义
2. `ygb` 是否真正成为企业与人社侧主工作台
3. `azb` 是否真正成为应急与安责险侧主工作台
4. 高频用户是否不再被基础 CRUD 页面拖慢

达到这四点，双前端改造才算完成；否则就只是把菜单分到了两个目录里。
