# 双前端功能拆解定案

日期：2026-06-05

## 1. 结论先行

粤工保与安责保必须按“一套后台、两个前端门户、共享业务内核、分离页面语义”长期建设，不能继续理解为“同一套后台页面换两个登录页”。

固定结论如下：

1. 后端只保留一套业务域模型、一套主数据、一套状态机、一套权限底座。
2. 前端固定拆为 `ygb` 与 `azb` 两个门户，登录页、首页、菜单、模块首页、详情页重点、默认动作允许不同。
3. 共性模块共享数据与接口，不强行共享同一张页面。
4. `ygb` 承接企业办理、人社监管、财务整改主链路。
5. `azb` 承接应急治理、安责险协同、风险处置主链路。
6. 评分体系 `6.1` 不再单独做一套页面，而是挂接到双门户现有共享模块之上，分别输出不同解释口径。

## 2. 双门户长期定位

### 2.1 粤工保 `ygb`

长期定位：

- 企业管理员工作台
- 企业经办员录入与补录工作台
- 人社监管工作台
- 财务整改与归档工作台

页面语义关键词：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

### 2.2 安责保 `azb`

长期定位：

- 应急治理工作台
- 安责险协同工作台
- 现场风险处置工作台
- 银保协同只读工作台

页面语义关键词：

- 风险
- 治理
- 处置
- 时效
- 在途
- 重点对象

## 3. 角色与门户归位

| 角色 | 默认门户 | 主职责 | 页面风格 |
| --- | --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 企业管理、统筹办理、闭环推进 | 强操作 |
| `105 ygb_enterprise_operator` | `ygb` | 录入、导入、修改、结束登记 | 轻决策、强校验 |
| `106 ygb_hrss_supervisor` | `ygb` | 人社监管、区域异常、归档核查 | 强摘要、强统计 |
| `107 ygb_emergency_supervisor` | `azb` | 应急监管、重大风险处置 | 强焦点、强时效 |
| `108 ygb_insurer` | `azb` | 保单、预防资金、信用复核 | 只读协同 |
| `109 ygb_bank` | `azb` | 工资风险、信用、报表协同 | 只读协同 |

固定规则：

1. `104/105/106` 默认进入 `ygb`。
2. `107/108/109` 默认进入 `azb`。
3. `108/109` 默认只保留摘要、详情、导出、报表下钻。
4. 企业业务主链不进入 `azb` 主菜单。
5. 应急治理主链不进入 `ygb` 主菜单。

## 4. 功能拆解总原则

一个模块命中以下任意两条，就必须按“双视图共享模块”处理：

1. 两边的主要使用角色不同。
2. 两边进入模块后的首要动作不同。
3. 两边首页入口优先级不同。
4. 两边详情页最关注的信息不同。
5. 两边默认筛选条件不同。
6. 两边按钮密度和操作深度不同。

不命中以上两条的模块，才允许继续单门户落地。

## 5. 模块归属定案

| 模块 | 后台是否共享 | `ygb` 语义 | `azb` 处理 |

| 原始考勤 / 月归集 | 共享后台 | 考勤办理与归集 | 不进主菜单 |
| 工资批次 / 工资明细 | 共享后台 | 发薪闭环与对账 | 仅允许银行看摘要结果 |
| 社保比对 / 欠费整改 | 共享后台 | 参保整改 | 不进主菜单 |
| 个税比对 | 共享后台 | 财务整改 | 不进主菜单 |
| 用工比例 / 假外包识别 | 共享后台 | 合规整改 | 不进主菜单 |
| 新业态人员库 / 职业病监测 | 共享后台 | 专项监管 | 不进主菜单 |

### 5.3 `azb` 主责模块

`azb` 当前没有完全独立于 `ygb` 主数据之外的新业务库，但以下页面应明确由 `azb` 侧主导表达：

1. `azb/cockpit`
2. `azb/device`
3. `azb/warning`
4. `azb/heightWorkReport`
5. `azb/aqInsurance`
6. `azb/aiReport`
7. `azb/creditScore`

这些模块虽然共享后台对象，但不应再退回通用 CRUD 语义。

## 6. 530.1 到双门户的分解口径

### 6.1 企业办理链路落在 `ygb`

530.1 中以下需求应落到 `ygb` 主链路：

1. 合同、考勤、工资、社保、税务、用工比例、假外包等企业办理闭环。
2. 企业管理员与经办员的录入、导入、修改、结束登记、归档。
3. 人社监管对区域异常、整改闭环、归档报表的查看与督办。
4. 工伤申报认定申领链路。
5. 高处作业报备的企业留痕和结束登记。

### 6.2 风险治理链路落在 `azb`

530.1 中以下需求应落到 `azb` 主链路：

1. 设备在线、离线、围栏、AI 风险治理。
2. 安责险保单、预防资金、预防项目协同。
3. 高处作业在途风险、异常证书、超时未结束的处置。
4. 事故、预警、重大风险对象的时效性治理。
5. 区域态势、驾驶舱、只读协同角色的下钻。

## 7. 6.1 评分体系挂接定案

### 7.1 `ygb` 的评分解释主链

| 评分维度 | 主挂接模块 | 解释目标 |
| --- | --- | --- |
| 工伤预防 | 工伤事件、预防项目、预防资金、统计报表 | 看发生率、整改率、归档率 |
| 用工合规 | 合同、考勤、工资、社保、税务、用工比例、假外包 | 看异常对象与整改闭环 |
| 参保扩面 | 社保、安责险、漏保清单 | 看覆盖率、补保率、督办完成率 |
| 预警处置 | 预警中心、规则、AI 报告 | 看待办量、超时量、闭环率 |
| 技术防范 | 高处作业、设备、AI 报告 | 看报备留痕、设备稳定、风险压降 |

### 7.2 `azb` 的评分解释主链

| 评分维度 | 主挂接模块 | 解释目标 |
| --- | --- | --- |
| 安责险合规 | 安责险、预防资金、预防项目 | 看投保覆盖、资金健康、项目成效 |
| 设备安全 | 设备、预警、工伤事件 | 看在线率、离线时长、异常处置 |
| 技术防范 | 高处作业、AI 报告、设备 | 看高危作业在途风险与识别结果 |
| 隐患整改 | 预警中心、AI 报告、设备 | 看红警对象、重复隐患、超时未闭环 |
| 应急响应 | 驾驶舱、统计报表、区域队列 | 看区域态势、重点对象、处置时效 |

### 7.3 固定口径

1. 同一企业可在 `ygb` 与 `azb` 共用同一批底数。
2. 双门户必须输出不同的评分解释，不再共用同一套摘要文案。
3. 权重与得分点优先通过模型配置维护，不把规则写死在页面里。

## 8. 接口与数据边界

后端固定遵循：

1. 业务主表、明细表只保留一套。
2. 列表、详情、导出接口继续共用。
3. 门户差异通过 `summary/dashboard/detail` 聚合层输出。
4. 菜单显隐通过 `portal_scope`、角色默认门户、角色可访问门户控制。
5. 只读角色在后端继续做权限兜底，不只依赖前端隐藏按钮。

## 9. 页面落地标准

### 9.1 `ygb` 页面

高频页面统一采用：

1. 顶部业务定位说明
2. 摘要卡
3. 办理焦点
4. 当前选中对象
5. 办理路径
6. 搜索区
7. 工具栏
8. 台账表格
9. 详情抽屉

### 9.2 `azb` 页面

高频页面统一采用：

1. 顶部治理定位说明
2. 摘要卡
3. 焦点队列
4. 当前风险对象
5. 当前处置建议
6. 风险提示
7. 搜索区
8. 工具栏
9. 治理台账
10. 详情抽屉

## 10. 直接可执行的落地顺序

1. 先完成双门户模块归属与角色默认门户兜底。
2. 再完成首页与驾驶舱的双门户工作台化。
3. 然后按共享模块批次做 `ygb/azb` 双视图改造。
4. 再把 530.1 底数接入 6.1 评分解释。
5. 最后统一收口 SQL、菜单、按钮权限、验收口径。

## 11. 最终定案

1. 双前端不是视觉差异项目，而是同一底座上的双语义业务系统。
2. 共性高，证明应共享后端，不证明应共享页面。
3. 粤工保主攻“办理闭环”，安责保主攻“风险治理”。
4. 后续所有新模块都先按本定案判断：`ygb` 独占、`azb` 主责，还是双视图共享模块。
