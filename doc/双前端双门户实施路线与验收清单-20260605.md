# 双前端双门户实施路线与验收清单

## 1. 目标

本清单直接服务开发排期、联调和验收，不讨论概念，只回答三件事：

1. 先做什么
2. 后端补什么
3. 验收怎么过

范围限定为当前 `YueGongBao-Vue` 单后台仓库，不单独拆新服务，不新建第二套后台表。

## 2. 实施原则

### 2.1 后端原则

- 统一 CRUD
- 统一状态机
- 统一主数据
- 优先补 `summary/dashboard`
- 权限以 `portal_scope + role + perm` 三层控制

补充要求：

- 不再新建“粤工保后台”和“安责保后台”两套服务
- 允许补门户聚合接口，不允许为同一业务对象复制两套 CRUD
- 高危、预警、设备、安责险、AI 等对象优先做“共内核 + 双聚合 + 双视图”

### 2.2 前端原则

- `ygb` 与 `azb` 固定为两套工作台，不再共用一页兼顾两种语义
- 共享模块必须拆 `views/ygb` 和 `views/azb`
- 只读角色先在前端收口，再由后端权限兜底
- 工作台页必须支持“摘要 + 表格 + 当前对象 + 详情联动”

补充要求：

- `ygb` 以企业办理效率为优先
- `azb` 以风险处置效率为优先
- 共享组件可以复用，但最终页面语义不能混写

### 2.3 发布原则

- 优先改高频模块，不先铺低频管理页
- 优先补聚合，不复制更多 CRUD
- 每一批次都要求 `ygb` 和 `azb` 至少有一个用户场景闭环

## 3. 当前代码可直接承接的底座

已具备：

- 登录页门户品牌区分
- `X-Portal-Code`
- `sys_menu.portal_scope`
- `sys_role.allowed_portal_scope`
- `sys_role.default_portal_code`
- `sys_role_menu.portal_scope`
- 角色跨门户自动归位
- `ygb-business.scss` 与 `azb-business.scss` 两套共享工作台样式

因此后续改造的重点不再是底层框架，而是模块工作台化和评分口径化。

| 能力 | 动作 |
| --- | --- |
| `summary` 接口 | 为 `taxCompare`、`employmentRatio`、`fakeOutsourcing`、`newformWorker`、`occupationMonitor` 补聚合字段 |

### 前端固定结构

每页固定按以下结构实现：

1. 顶部业务定位
2. 摘要卡
3. 办理焦点
4. 当前选中对象
5. 办理路径
6. 搜索区
7. 工具栏
8. 表格
9. 详情抽屉

### 本批验收

1. 企业管理员进入页面，3 秒内能知道当前待处理对象是谁
2. 摘要来自后端，不从当前页数据临时计算
3. 行点击联动当前对象与详情抽屉
4. 构建通过 `vite build --mode ygb`

## 4.3 P2 评分体系接入批

### 目标

让 `530.1` 模块数据正式转成 `6.1` 评分口径，而不是停留在静态台账。

### 后端动作

3. 权重调整不需要改代码逻辑

## 4.4 P3 双门户首页与角色入口收口批

### 目标

把“两个登录页不同”进一步升级为“两个门户进入系统后的首屏工作方式也不同”。

### 动作

| 类型 | 动作 |
| --- | --- |
| 首页工作台 | `ygb` 首页突出待办、整改、财务闭环；`azb` 首页突出红警、在途高危、设备异常、治理时效 |
| 角色默认入口 | `104/105/106` 固定走 `ygb` 首页队列；`107/108/109` 固定走 `azb` 首页队列 |
| 快捷入口 | `ygb` 放合同、考勤、工资、高处作业；`azb` 放驾驶舱、设备、预警、高处作业 |
| 只读轻视图 | `108/109` 在首页只保留摘要、报表、详情跳转，不进入复杂维护页 |

### 验收

1. 不同角色登录后的首屏重点对象明显不同
2. `ygb` 首屏不会被安责保治理语义污染
3. `azb` 首屏不会出现企业劳务办理主链入口

## 5. 每类模块的接口补齐规则

### 5.1 `ygb` 独占模块

适用：

- 工资
- 社保
- 个税
- 用工比例
- 假外包
- 新业态
- 职业病

补齐要求：

- 保留统一 CRUD
- 必须增加 `summary`
- 首页可复用的待办要沉淀成聚合接口

### 5.2 双视图共享模块

适用：

- 单位
- 人员
- 预警
- 设备
- 安责险
- 工伤
- 预防资金
- 预防项目
- 高处作业
- AI 报告
- 统计报表
- 信用评价
- 漏保清单
- 驾驶舱

补齐要求：

- CRUD 不复制
- `summary/dashboard` 按门户拆
- 详情接口允许补充门户侧字段，但不复制主表

双前端页面补齐时统一检查以下四项：

1. 是否已有门户摘要接口
2. 是否已有当前对象联动能力
3. 是否已有只读角色按钮收口
4. 是否已有 `ygb/azb` 两套详情重点

### 5.3 只读协同角色模块

适用：

- `108`
- `109`

补齐要求：

- 单独提供轻视图展示策略
- 前端隐藏新增、修改、结束、同步、指令、启停、版本维护
- 后端对敏感接口继续校验权限

建议统一沉淀一个“轻视图判定层”：

- 角色键命中 `ygb_insurer`、`ygb_bank`
- 页面自动降级成只读摘要模式
- 表格保留查询、详情、导出
- 详情页保留业务解释，不开放维护动作

这样后续双门户共享页无需每次重复发明一套只读处理逻辑。

## 7. 页面设计和交互硬标准

### 7.1 `ygb` 页面硬标准

- 页面标题必须体现“办理台账、整改台账、归档台账”语义
- 操作栏必须服务企业经办和财务闭环
- 详情抽屉必须说明“下一步怎么处理”

### 7.2 `azb` 页面硬标准

- 页面标题必须体现“治理台账、风险台账、处置中心”语义
- 摘要卡优先呈现风险数量、处置时效、异常对象
- 详情抽屉必须说明“是否已处置、是否超时、是否重复发生”

### 7.3 典型用户的交互标准

#### 企业管理员

- 进入页面先看待办量、异常量、截止时间
- 常用动作不能超过两次点击
- 批量导入导出、整改回填必须在主操作栏可见

#### 工地负责人

- 进入页面先看现场对象和在途事项
- 高处作业、预警、设备状态必须能快速切换
- 详情里必须直接看到联系人、时间、位置、凭证或完成佐证

#### 操作员

- 更关注录入、同步、修正、重提
- 页面要减少无关统计噪音
- 表单校验和导入反馈要明确

#### 财务

- 更关注工资、社保、个税、专户和对账结果
- 页面要突出异常原因和导出能力
- 不要让财务先穿过治理类入口再去办业务

## 8. 测试清单

### 8.1 登录与门户

1. `104/105/106` 默认进入 `ygb`
2. `107/108/109` 默认进入 `azb`
3. `107/108/109` 持 token 访问 `ygb` 自动归位
4. 两个登录页品牌、引导语、首页入口明显不同

### 8.2 菜单与按钮

1. `azb` 看不到合同、考勤、社保、个税等 `ygb` 主链
2. `ygb` 不默认暴露安责保治理专属入口
3. `108/109` 只保留查询、详情、导出、报表
4. 共享模块在 `ygb/azb` 的按钮密度和详情重点不同

### 8.3 页面体验

1. 页面不是只有表格和弹窗
2. 摘要、焦点、当前对象、详情联动完整
3. 企业管理员、财务、应急监管、保险协同四类用户都能快速定位对象

### 8.4 数据与评分

1. 同一企业的数据在两个门户一致
2. 同一企业在两个门户的解释口径不同
3. 评分结果可追溯到业务表来源

### 8.5 模块拆解验收

1. 新模块立项时，必须先写清楚是“`ygb` 独占 / 双门户双视图 / `azb` 重点治理入口”哪一类
2. 双门户共享模块必须同时给出“共后台能力”和“门户差异能力”
3. 不允许再提交“一个页面兼容两种门户语义”的长期方案
4. 只读角色的前端隐藏与后端兜底必须同时存在

## 9. 当前最合理的下一步

直接按下面顺序推进：

1. 先完成 `ygb/taxCompare`
2. 再完成 `ygb/employmentRatio`
3. 再完成 `ygb/fakeOutsourcing`
4. 然后补 `newformWorker` 与 `occupationMonitor`
5. 完成后再进入 `azb` 角色化首页深化和评分字段接入

这样排期的原因是：

- 当前 80% 的真实高频需求仍然在 `ygb`
- 财务整改链是企业侧最长、最高频、最容易暴露体验缺陷的主链
- `azb` 当前底座和主要治理页已基本成型，更适合放在下一批做角色细分和评分深化
