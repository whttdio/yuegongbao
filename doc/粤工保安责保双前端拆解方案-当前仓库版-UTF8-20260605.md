# 粤工保 / 安责保双前端拆解方案（当前仓库版）

日期：2026-06-06

## 1. 结论先行

当前系统应固定为“一套后台、两个前端、两套门户语义”的长期架构。

这不是“同一套页面换两个登录页”，而是：

- 后台业务对象单源
- 数据口径单源
- 接口主链单源
- 菜单、角色、首页、驾驶舱、详情重点、推荐动作按门户分流

结合 `粤工保开发需求分析说明书（530.1版）` 与 `评分体系细化得分点6.1`，可以落成三个硬结论：

1. “七成共性”只说明后台应共用，不说明页面应继续共用。
2. “八成内容偏粤工保”说明 `ygb` 是主业务门户，`azb` 是监管治理门户，不是对半拆。
3. 人社监管与应急监管的大量重叠能力，正确做法是“同对象、双入口、双摘要、双详情重点”，而不是复制第二套表和第二套接口。

## 2. 两个前端各自承担什么

### 2.1 粤工保 `ygb`

长期定位固定为：

- 企业管理员工作台
- 企业经办工作台
- 财务整改工作台
- 人社监管工作台

核心语义固定为：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

它主要承接 `530.1` 中的主业务链：合同、考勤、工资、社保、税务、扩面减损、企业基础管理、报表归档。

### 2.2 安责保 `azb`

长期定位固定为：

- 应急监管工作台
- 安责险协同工作台
- 风险治理工作台
- 现场安全视角工作台

核心语义固定为：

- 风险
- 处置
- 时效
- 在途
- 重点对象
- 区域治理

它主要承接 `6.1` 的治理解释链：设备安全、安责险覆盖、高危作业、AI 风险识别、预警闭环、区域态势。

## 3. 为什么不能只做一套页面

如果一个模块同时满足以下任意两条，就必须走“共享业务逻辑 + 双门户页面”：

1. 主要使用角色不同
2. 首要动作不同
3. 首页入口优先级不同
4. 首屏摘要卡不同
5. 焦点队列不同
6. 详情页重点不同
7. 按钮密度与操作深度不同

所以：

- 字段一样，不等于页面应该一样
- 接口一样，不等于工作台应该一样
- 数据打通麻烦，更说明后台要统一，不说明前端要强行共页

## 4. 一套后台必须共用的边界

以下对象必须保持单源，不能按门户复制第二套业务表：

- 企业
- 人员
- 合同
- 考勤
- 工资
- 社保
- 税务
- 预警
- 预警规则
- 设备
- 高处作业申报报备
- 工伤事件
- 安责险保单
- 事故预防项目
- 事故预防资金
- AI 原始事件 / AI 报告 / AI 配置
- 信用评分底数
- 统计报表底数
- 首页 / 驾驶舱聚合底数
- 角色 / 菜单 / 门户范围

共享后台的正确含义是：

- 一套业务表
- 一套状态机
- 一套主接口
- 一套校验规则
- 一套导入导出主逻辑

共享后台不等于：

- 共享首页
- 共享工作台文案
- 共享详情结构
- 共享动作优先级

## 5. 角色与门户定案

| 角色 | 默认门户 | 长期定位 | 页面重点 |
| --- | --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 企业管理员 | 合同、考勤、工资、社保、预警、高处作业闭环 |
| `105 ygb_enterprise_operator` | `ygb` | 企业经办员 | 录入、导入、修正、回写、结束登记 |
| `106 ygb_hrss_supervisor` | `ygb` | 人社监管员 | 劳务合规、扩面减损、工伤预防、区域监管 |
| `107 ygb_emergency_supervisor` | `azb` | 应急监管员 | 红警、设备、高危作业、AI 风险、处置时效 |
| `108 ygb_insurer` | `azb` | 保险公司 | 保单风险、预防资金、信用评价、区域报表 |
| `109 ygb_bank` | `azb` | 银行 | 工资风险摘要、信用评价、统计报表 |

固定规则：

1. `104/105/106` 默认进入 `ygb`
2. `107/108/109` 默认进入 `azb`
3. `108/109` 统一走轻视图，只保留摘要、详情、导出、报表
4. 企业角色允许访问双门户时，`ygb` 仍为主入口
5. `azb` 只承接治理与监管表达，不承接完整劳务办理流程

## 6. 按模块拆解的最终归属

### 6.1 只做 `ygb` 完整工作台的模块

这些模块属于企业办理主链，不建议在 `azb` 再做完整页面：

- 合同备案 `contract`
- 原始考勤 `attendanceRaw`
- 月度考勤 `attendanceMonthly`
- 工资批次 `salaryBatch`
- 工资明细 `salaryDetail`
- 社保缴费 `socialPayment`
- 社保基数比对 `socialBaseCompare`
- 个税比对 `taxCompare`
- 用工比例 `employmentRatio`
- 假外包识别 `fakeOutsourcing`
- 新业态人员 `newformWorker`
- 职业病监测 `occupationMonitor`

`azb` 如需使用，只引用摘要结果、风险结论、评分解释，不再承接原办理页。

### 6.2 必须做双视图的共享模块

这些模块后台共用，但页面必须双门户表达：

- 首页工作台 `home`
- 驾驶舱 `cockpit`
- 单位管理 `enterprise`
- 人员管理 `person`
- 预警中心 `warning`
- 预警规则 `warningRule`
- 设备管理 `device`
- 安责险管理 `aqInsurance`
- 事故预防资金 `preventionFund`
- 事故预防项目 `preventionProject`
- 工伤事件 `injuryEvent`
- 高处作业申报报备 `heightWorkReport`
- AI 监测报告 `aiReport`
- AI 模型配置 `aiReportConfig`
- 信用评价 `creditScore`
- 统计报表 `statReport`
- 漏保清单 `uninsuredList`

双视图的固定分工：

- `ygb` 强调办理、整改、回写、归档、月报闭环
- `azb` 强调风险、在途、时效、重点对象、区域治理

### 6.3 `azb` 主责强化的模块

这些模块虽然仍共后台，但前台表达应明显偏向 `azb`：

- 安责险管理
- 设备安全治理
- 技术防范 / 高处作业
- AI 风险研判
- 区域安全态势
- 隐患闭环联动
- 评分体系 6.1 解释页

### 6.4 按 `530.1` 一级模块的执行拆解矩阵

| `530.1` 一级模块 | 双前端落地方式 | 当前执行结论 |
| --- | --- | --- |
| 驾驶舱 | 双视图 | `ygb` 负责企业办理总览，`azb` 负责治理总览，继续共用聚合底数 |
| 预警中心 | 双视图 | 同一预警工单与规则底数，`ygb` 看办理闭环，`azb` 看风险处置时效 |
| AI 监测报告 | 双视图 | 同一报告与模型底数，`ygb` 看归档与整改，`azb` 看研判与压降 |
| 合同备案 | `ygb` 完整页 | `azb` 不再承接原办理页，只允许后续引用摘要结果 |
| 用工考勤 | `ygb` 完整页 | `azb` 不做考勤办理页，只消费风险摘要 |
| 工资监管 | `ygb` 完整页 | `azb` 仅保留银行与监管侧工资风险摘要，不承接发薪闭环 |
| 社保监管 | `ygb` 完整页 | `azb` 不承接缴费与基数整改流程 |
| 工伤监管 | 双视图 | `ygb` 侧偏认定申报与归档，`azb` 侧偏事故协同与风险联动 |
| 专项治理 | `ygb` 完整页 | 用工比例、假外包继续放在 `ygb` 主链，不拆第二套治理页 |
| 税务监管 | `ygb` 完整页 | 个税比对仍归财务整改主链 |
| 安责险管理 | 双视图，`azb` 主责强化 | 同后台保单与资金底数，`azb` 负责主治理表达 |
| 设备管理 | 双视图，`azb` 主责强化 | 同后台设备台账与指令链，`azb` 负责安全治理表达 |
| 扩面减损 | 双视图 | 底数同源，`ygb` 看催缴补缴闭环，`azb` 看风险对象与区域治理 |
| 信用评价 | 双视图 | 同评分底数，`ygb` 看合规评分，`azb` 看风险分层 |
| 统计报表 | 双视图 | 同报表底数，`ygb` 看月报归档，`azb` 看区域态势与治理月报 |
| 人员管理 | 双视图 | 同人员主数据，`ygb` 看主数据办理，`azb` 看风险准入对象 |
| 单位管理 | 双视图 | 同企业主数据，`ygb` 看主体办理，`azb` 看治理对象 |
| 系统管理 | 后台通用能力 | 不按 `ygb/azb` 业务语义拆页面，重点是菜单 `portal_scope` 与角色矩阵 |
| 运营后台 | 后台通用能力 | 不进入当前双门户主链，保持独立后台能力 |
| 企业后台 | 归入 `ygb/home` 语义 | 不再单独复制一套企业端工作台，统一收口到 `ygb` 首页与业务页 |
| 便民服务 | 暂不纳入双门户主链 | 若后续接入，按独立公众端处理，不混进 `ygb/azb` 监管门户 |
| 新业态监管 | `ygb` 完整页 | 归人社监管与企业办理主链 |
| 职业病监管 | `ygb` 完整页 | 归人社监管与专项监管主链 |
| 高处作业申报报备 | 双视图，`azb` 主责强化 | 同报备底数，`ygb` 看留痕办理，`azb` 看高危作业治理 |

## 7. 530.1 与 6.1 应如何挂接

### 7.1 `ygb` 的解释口径

`ygb` 对评分的解释应围绕“业务办理价值”展开：

- 劳务合规
  - 合同、考勤、工资、社保、个税、用工比例、假外包
- 工伤预防
  - 工伤事件、预防项目、预防资金
- 扩面减损
  - 漏保、参保覆盖、催缴与补缴
- 预警闭环
  - 预警中心、规则、AI 报告
- 技术防范留痕
  - 高处作业、设备接入、AI 识别结果

页面表达重点应是：

- 当前异常对象
- 办理堵点
- 整改完成率
- 月报归档结果

### 7.2 `azb` 的解释口径

`azb` 对同一底数的解释应围绕“治理成效”展开：

- 安责险合规
  - 投保覆盖、保单有效、预防资金健康度
- 设备安全
  - 在线率、离线时长、授权状态、处置时效
- 技术防范
  - 高危作业在途、证书异常、AI 风险压降
- 隐患整改
  - 重大隐患、重复隐患、超时未闭环
- 应急响应
  - 区域态势、重点对象、协同处置效率

页面表达重点应是：

- 风险对象队列
- 当前风险等级
- 处置时效
- 区域治理焦点

### 7.3 固定挂接原则

1. 同一企业在 `ygb` 和 `azb` 共用同一底数
2. 同一底数在两个门户必须输出不同解释顺序
3. 评分调整优先通过配置完成，不把权重写死到页面

- `ygb/uninsuredList` 已继续深化为“角色感知 + 焦点队列 + 动态主动作”的漏保整改工作台，不再只是统一漏保列表。

- `ygb/aiReportConfig` 已继续深化为“角色感知 + 焦点队列 + 动态主动作”的评分模型办理工作台，不再只是通用配置列表。
- 当前剩余问题的主线已经从“模块是否要拆”转为“每个共享模块的 `ygb` 办理语义和 `azb` 治理语义是否足够深”。 

## 10. 后续新增模块的统一判断模板

以后每新增一个模块，立项前必须先回答 8 个问题：

1. 它是 `ygb` 独占、`azb` 主责，还是共享双视图
2. 主数据是否继续共后台
3. 是否需要 `summary` / `dashboard` 聚合接口
4. `ygb` 与 `azb` 的默认入口是否不同
5. 两个门户的详情重点是否不同
6. `108/109` 是否需要轻视图
7. 它挂到 `6.1` 的哪个评分解释域
8. 首页是否需要放快捷入口或焦点队列

这 8 个问题没回答清楚，就不应直接进入页面开发。

## 11. 最终拆解定案

1. 一套后台、两个前端，是当前项目最稳妥、成本最低、长期可维护的方向。
2. “七成共性”应该落在后台共用，不应该误用成“七成页面共用”。
3. `ygb` 是企业办理主门户，`azb` 是监管治理主门户，两者必须长期并行，不应相互退化成换皮页。
4. 所有重叠模块都按“同对象、双入口、双摘要、双详情重点”落地。
5. 后续研发、菜单注入、接口补充、验收测试，都应以本方案作为模块归属的准绳。
