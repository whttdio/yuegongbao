# 双前端业务模块拆解方案

## 1. 目标与判断依据

本方案用于回答一个核心问题：`一套后台、两个前端` 应该如何拆，才能既保证数据打通，又避免两个监管部门在同一个界面里互相干扰。

判断依据来自三部分：

- 需求总文档：[需求分析说明书530.1版.md](D:/work/yuegongbao/后台需求/需求分析说明书530.1版.md)
- 评分体系文档：[粤工保与安责保平台评分体系细化得分点6.1.docx](D:/work/yuegongbao/后台需求/粤工保与安责保平台评分体系细化得分点6.1.docx)
- 当前代码现状：
  - 门户配置：[portal.js](/D:/javaproject/yuegongbao/YueGongBao-Vue/yuegongbao-ui/src/config/portal.js)
  - 门户运行时工具：[portal.js](/D:/javaproject/yuegongbao/YueGongBao-Vue/yuegongbao-ui/src/utils/portal.js)
  - 实施清单：[双前端技术改造实施清单.md](/D:/javaproject/yuegongbao/YueGongBao-Vue/doc/双前端技术改造实施清单.md)
  - 门户 SQL：[ygb_phase9_dual_portal_scope.sql](/D:/javaproject/yuegongbao/YueGongBao-Vue/sql/ygb_phase9_dual_portal_scope.sql)

文档结论很明确：

- `530.1` 强调“数据同源”，企业和人员必须共主表。
- 粤工保侧主责是 `合同 / 考勤 / 工资 / 社保 / 个税 / 用工合规`。
- 安责保侧主责是 `安责险 / 设备 / AI识别 / 风险预警 / 事故预防 / 高危作业治理`。
- 评分体系明确拆成 `粤工保（人社侧）` 和 `安责保（应急侧）` 两套口径，因此 `AI报告、驾驶舱、统计展示` 不能只换皮，必须按门户重组。

## 2. 总拆分原则

### 2.1 后台只保留一套

- 企业、人员、预警、设备、高处作业、AI原始数据统一入一套后台。
- 不拆库、不复制表、不复制核心业务状态机。
- 后台负责：
  - 统一数据模型
  - 统一权限底座
  - 统一接口
  - 按 `portal_scope` 和 `X-Portal-Code` 做菜单与按钮收敛

### 2.2 前端必须拆成两个工作台

- `ygb` 不是“大而全后台”，而是 `人社监管 + 企业劳务合规工作台`。
- `azb` 不是“粤工保子频道”，而是 `应急监管 + 安责险治理工作台`。
- 相同数据在两个门户可以复用，但：
  - 导航结构不同
  - 首页优先级不同
  - 指标口径不同
  - 详情页摘要不同
  - 操作按钮不同

### 2.3 共性模块不等于共用页面

共性模块只说明 `后端和基础表可共用`，不说明页面可以永远共用。

模块拆分应分成三层：

1. `后台共用`
2. `前端包装复用`
3. `前端独立视图`

高频模块最终应尽量落到第 3 层。

## 3. 从业务视角看两个门户

### 3.1 粤工保门户的核心用户

- 企业管理员
- 工地负责人
- 操作员
- 财务经办
- 人社监管员

他们的高频动作是：

- 合同备案
- 考勤上报与归集
- 工资批次处理
- 社保/个税比对
- 漏保整改
- 人员工伤预防与参保扩面

因此 `ygb` 首页应该围绕 `填报、对账、整改、闭环` 组织。

### 3.2 安责保门户的核心用户

- 应急监管员
- 保险公司
- 企业现场安全负责人
- 设备管理员
- 高危作业现场负责人

他们的高频动作是：

- 看设备在线和告警
- 看安责险覆盖和到期风险
- 看 AI 识别隐患和工单处置
- 看高处作业报备与结束
- 看整改闭环和监管联动

因此 `azb` 首页应该围绕 `风险发现、现场处置、闭环跟踪、监管评分` 组织。

## 4. 模块拆解结论

### 4.1 粤工保独占模块

这些模块只在 `ygb` 完整呈现，`azb` 不应暴露菜单，也不应出现按钮权限：

- 合同备案
- 考勤上报
- 考勤归集
- 工资批次
- 工资明细
- 社保比对
- 社保基数比对
- 个税比对
- 用工比例
- 假外包识别
- 新业态人员库

原因：

- 这些模块服务的是人社监管和企业劳务合规。
- 安责保评分体系并不以这些页面作为主操作入口。
- 即使个别数据会被安责保评分引用，也应通过共享数据结果透出，不应直接暴露原业务工作台。

### 4.2 后台共用、双前端展示模块

这些模块应保留统一后端，但两个前端都要有自己的页面表达：

- 单位管理
- 人员管理
- 预警中心
- 预警规则
- 设备管理
- 安责险管理
- 工伤事件
- 事故预防资金池
- 预防项目
- 高处作业申报报备
- AI监测报告
- AI监测配置
- 统计报表
- 信用评价
- 漏保清单

其中再分两类：

- `azb 已独立页`：`cockpit / warning / device / aqInsurance / statReport / creditScore / preventionFund / preventionProject / injuryEvent / heightWorkReport / aiReport / aiReportConfig / person / enterprise / uninsuredList / warningRule`
- `仍需继续增强门户聚合`：`首页工作台 / 首页快捷入口 / 驾驶舱聚合 / AI报告首页摘要 / 统计报表门户说明`

### 4.3 安责保独占视图模块

这些不一定新增后端表，但在 `azb` 必须有独立工作台表达：

- 安责险监管视图
- 设备安全治理视图
- 现场风险预警视图
- 高危作业治理视图
- 事故预防资金治理视图
- 应急侧驾驶舱

原因：

- 评分体系已经把应急侧指标拆成独立维度。
- 这些页面的第一诉求不是“录入数据”，而是“快速识别风险并指挥处置”。

## 5. 前后端边界建议

### 5.1 后端必须继续共用的部分

- `t_enterprise`、`t_person` 主数据
- 预警事件与工单状态机
- 设备与 AI 原始事件
- 高处作业主表与人员明细
- AI 评分原始结果与历史快照
- 角色、菜单、按钮权限体系

### 5.2 后端需要按门户差异化的部分

- `getRouters`
- `getInfo`
- 驾驶舱汇总接口
- AI报告首页看板接口
- 统计报表说明和推荐模板
- 菜单树与按钮权限返回结果

原则不是复制控制器，而是：

- 共用查询内核
- 允许独立汇总接口
- 允许不同门户对同一数据做不同口径封装

### 5.3 前端必须独立承载的部分

- 登录页
- 门户首页
- 首页快捷入口
- 驾驶舱
- AI报告首页与摘要
- 高危治理页摘要卡片
- 模块顶部说明文案
- 报表说明和导出入口布局

## 8. 建议的最终结构

### 8.1 粤工保前端定位

- 一套偏 `企业办理 + 人社监管` 的业务工作台
- 页面中心是：
  - 台账录入
  - 对账比对
  - 整改闭环
  - 财务批处理

### 8.2 安责保前端定位

- 一套偏 `风险治理 + 应急监管 + 保险协同` 的治理工作台
- 页面中心是：
  - 态势总览
  - 风险识别
  - 现场联动
  - 工单闭环

### 8.3 统一后台定位

- 做共表、共接口、共权限
- 不承载某一门户的页面语义
- 所有门户差异优先收敛在：
  - 菜单归属
  - 角色矩阵
  - 汇总接口
  - 前端视图层

## 9. 最终落地建议

1. 把“共性模块”定义成 `后端共用`，不要继续理解成 `页面共用`。
2. `ygb` 保持 80% 主业务承载，但不要让 `azb` 长期做 Banner 包装站。
3. `azb` 页面层面的独立视图已经基本齐备，下一阶段重点转为“首页工作台 + 门户聚合接口 + 角色默认入口”。
4. 后续所有新模块先判断：
   - 是否共表
   - 是否双门户可见
   - 是否两边统计口径不同
   - 是否两边首页入口不同
5. 只要统计口径或用户动作不同，就应按双前端独立页设计，而不是继续复制 `ygb` 页面。
