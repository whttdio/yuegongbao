# 粤工保 / 安责保双前端拆解方案（当前仓库版）

日期：2026-06-06

## 1. 结论先行

基于《粤工保开发需求分析说明书（530.1版）》与《粤工保与安责保平台评分体系细化得分点6.1》，当前系统应固定为：

- 一套后台
- 两个前端
- 一套业务底座
- 两套门户语义

这不是“同一套页面换两个登录页”，而是：

- 后台业务对象单源
- 数据口径单源
- 接口主链单源
- 登录页、首页、菜单树、工作台、驾驶舱、详情重点、推荐动作按门户分流

结合当前仓库事实，正确的长期方案是：

- `ygb` 承接 530.1 的企业办理主链和人社监管主链
- `azb` 承接 6.1 的安责险、技术防范、设备安全、风险治理解释链
- 共性模块共享后端，不共享工作台表达

## 2. 当前仓库已经具备的基础

当前仓库并非从零开始，双门户骨架已存在：

- 双登录入口：
  - `/login/ygb`
  - `/login/azb`
- 双构建模式：
  - `yuegongbao-ui/package.json`
  - `build:ygb`
  - `build:azb`
- 双门户配置：
  - `yuegongbao-ui/src/config/portal.js`
  - `yuegongbao-ui/src/utils/portal.js`
- 门户权限隔离：
  - 前端统一携带 `X-Portal-Code`
  - 后端按角色返回 `allowedPortalCodes` 与 `defaultPortalCode`
- 菜单门户边界：
  - `sys_menu.portal_scope`
  - `sql/ygb_phase9_dual_portal_scope.sql`
  - `sql/ygb_phase10_role_portal_scope.sql`
  - `sql/ygb_phase11_role_menu_portal_scope.sql`
- 页面目录已经按门户拆开：
  - `yuegongbao-ui/src/views/ygb`
  - `yuegongbao-ui/src/views/azb`

因此，接下来的工作重点不是再造第二套后台，而是把“双门户语义”彻底做实。

## 3. 拆解原则

### 3.1 什么必须共后台

以下对象必须保持单源，不能按门户复制第二套表和第二套主接口：

- 企业
- 人员
- 合同
- 考勤
- 工资
- 社保
- 税务
- 预警
- 预警规则
- 设备
- 安责险保单
- 高处作业申报报备
- 工伤事件
- 事故预防项目
- 事故预防资金
- AI 原始事件 / AI 报告 / AI 配置
- 信用评分底数
- 统计报表底数
- 角色 / 菜单 / 门户范围

共享后台的含义是：

- 一套业务表
- 一套状态机
- 一套主接口
- 一套校验规则
- 一套导入导出主逻辑

共享后台不等于：

- 共用首页
- 共用工作台文案
- 共用详情结构
- 共用首要动作

### 3.2 什么必须拆前端工作台

同一模块只要满足以下任意两条，就必须走“共业务逻辑 + 双门户页面”：

1. 主要使用角色不同
2. 首要动作不同
3. 首页入口优先级不同
4. 首屏摘要卡不同
5. 焦点队列不同
6. 详情页重点不同
7. 按钮密度与操作深度不同

因此：

- 字段一样，不代表页面应一样
- 接口一样，不代表工作台应一样
- 数据打通麻烦，反而更说明后台应统一，而不是前端硬共页

## 4. 两个前端各自承担什么

### 4.1 `ygb` 的长期定位

`ygb` 固定为：

- 企业管理员工作台
- 企业经办工作台
- 财务整改工作台
- 人社监管工作台

它的核心语义是：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

它主要承接 530.1 的业务办理链：

- 合同
- 考勤
- 工资
- 社保
- 税务
- 扩面减损
- 企业基础管理
- 统计归档

### 4.2 `azb` 的长期定位

`azb` 固定为：

- 应急监管工作台
- 安责险协同工作台
- 风险治理工作台
- 现场安全视角工作台

它的核心语义是：

- 风险
- 处置
- 时效
- 在途
- 重点对象
- 区域治理

它主要承接 6.1 的治理解释链：

- 安责险
- 设备安全
- 技术防范
- 高处作业
- AI 风险识别
- 预警闭环
- 区域态势

## 5. 模块最终归属

## 5.1 只做 `ygb` 完整工作台的模块

这部分属于企业办理主链，不建议在 `azb` 再做完整办理页：

- `contract`
- `attendanceRaw`
- `attendanceMonthly`
- `salaryBatch`
- `salaryDetail`
- `socialPayment`
- `socialBaseCompare`
- `taxCompare`
- `employmentRatio`
- `fakeOutsourcing`
- `newformWorker`
- `occupationMonitor`

`azb` 如果需要使用，只消费以下结果，不再承接原办理流程：

- 摘要结果
- 风险结论
- 评分解释
- 监管引用明细

## 5.2 必须做“双视图”的共底座模块

以下模块后端共享，但前端必须双门户表达：

- `home`
- `cockpit`
- `enterprise`
- `person`
- `warning`
- `warningRule`
- `device`
- `aqInsurance`
- `preventionFund`
- `preventionProject`
- `injuryEvent`
- `heightWorkReport`
- `aiReport`
- `aiReportConfig`
- `creditScore`
- `statReport`
- `uninsuredList`

双视图分工固定为：

- `ygb` 强调办理、整改、回写、归档、月报闭环
- `azb` 强调风险、在途、时效、重点对象、区域治理

## 5.3 `azb` 主责强化的模块

以下模块虽然仍共后台，但前台表达应明显偏向 `azb`：

- `aqInsurance`
- `device`
- `heightWorkReport`
- `warning`
- `warningRule`
- `aiReport`
- `aiReportConfig`
- `creditScore`
- `statReport`
- `preventionFund`
- `preventionProject`
- `injuryEvent`

原因很直接：

- 6.1 的评分解释链主要落在这些能力上
- 应急监管、保险机构、银行协同首先看的也是这些模块

## 5.4 不按门户拆业务页的模块

以下保持后台通用能力，不按 `ygb/azb` 再造业务页：

- 系统管理
- 菜单管理
- 角色管理
- 用户管理
- 字典管理
- 参数配置
- 日志审计
- 运营后台

重点是补强：

- 角色默认门户
- 角色允许门户
- 菜单 `portal_scope`
- 按门户授权树

## 6. 角色与门户归口

建议固定如下：

| 角色 | 默认门户 | 长期定位 |
| --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 企业管理员 |
| `105 ygb_enterprise_operator` | `ygb` | 企业经办员 |
| `106 ygb_hrss_supervisor` | `ygb` | 人社监管员 |
| `107 ygb_emergency_supervisor` | `azb` | 应急监管员 |
| `108 ygb_insurer` | `azb` | 保险机构 |
| `109 ygb_bank` | `azb` | 银行协同 |

固定规则：

1. `104/105/106` 默认进入 `ygb`
2. `107/108/109` 默认进入 `azb`
3. `108/109` 统一走轻视图，只保留摘要、详情、导出、报表
4. 企业角色允许访问双门户时，`ygb` 仍为主入口
5. `azb` 只承接治理与监管表达，不承接完整劳务办理流程

## 7. 前端应该怎么分，不应该怎么分

正确拆法：

- 共享 API composable / store / dict / domain model
- 拆门户 `view shell`
- 拆首页摘要
- 拆菜单树
- 拆工作台卡片与推荐动作
- 拆详情页默认关注点

错误拆法：

- 复制两套 backend controller
- 复制两套 table
- 复制两套 service
- 用 `if (portal === 'azb')` 把所有页面写成一页巨石
- 把 `azb` 降级成 `ygb` 的纯 banner 包装页

推荐前端分层：

1. 共享数据层
   - `src/api`
   - `src/views/*/useXxxPage.js`
   - `src/utils/roleView.js`

2. 门户外壳层
   - 登录页
   - 首页
   - 工作台
   - 驾驶舱
   - 详情摘要

3. 角色体验层
   - 企业管理员
   - 企业经办
   - 财务
   - 人社监管
   - 应急监管
   - 保险机构
   - 银行协同

## 8. 按 530.1 与 6.1 的统一解释口径

### 8.1 `530.1` 应主要落在 `ygb`

`530.1` 更偏业务办理、合规治理和企业主链，因此落地重点应是：

- 合同备案
- 用工考勤
- 工资监管
- 社保监管
- 税务监管
- 扩面减损
- 企业 / 人员基础管理
- 月报 / 归档 / 驾驶舱

### 8.2 `6.1` 应主要落在 `azb`

`6.1` 更偏评分解释、治理成效和安全视角，因此落地重点应是：

- 安责险
- 设备管理
- 技术防范
- 高处作业
- AI 监测报告
- 预警中心
- 信用评价
- 统计报表
- 项目 / 资金 / 治理闭环

### 8.3 两份文档的交集如何处理

交集模块不拆后台，只拆“解释方式”：

- 同一企业，在 `ygb` 看到的是业务办理结果
- 同一企业，在 `azb` 看到的是风险治理结果
- 同一条预警，在 `ygb` 看到的是整改闭环
- 同一条预警，在 `azb` 看到的是时效和升级风险
- 同一份 AI 报告，在 `ygb` 看到的是业务影响
- 同一份 AI 报告，在 `azb` 看到的是安全隐患与压降建议

## 9. 最终建议

最终架构不要再摇摆，直接定为：

- 一套后台
- 两个前端
- `ygb` 做主业务门户
- `azb` 做主治理门户
- 共性模块共享底座，但必须双视图落地

对于你提到的“七成内容一样、八成内容其实是粤工保要的”这件事，正确的工程解法不是回到一套前端，而是：

- 用一套后台解决数据打通
- 用两个前端解决监管语义和高频使用体验
- 用角色和菜单边界解决“谁看到什么、谁先做什么”

这才是既省后台成本，又不把前端做成四不像的方案。
