# 粤工保安责保双前端模块拆解定案（可执行版）

日期：2026-06-05

## 1. 文档目的

这份文档只解决四件事：

1. 一套后台、两个前端门户长期如何共存。
2. `530.1` 的业务模块应拆到 `ygb`、`azb` 还是双视图共享。
3. `6.1` 评分体系如何挂接到现有模块，而不是再做第三套页面。
4. 后续新增模块时，产品、前端、后端、测试按什么规则落地。

## 2. 当前代码事实

当前仓库已经不是“单后台 + 单前端”的状态，双前端底座已经存在：

- 路由已支持双登录入口：
  - `/login/ygb`
  - `/login/azb`
- 路由入口文件：
  - `yuegongbao-ui/src/router/index.js`
- 前端已拆成两个业务目录：
  - `yuegongbao-ui/src/views/ygb`
  - `yuegongbao-ui/src/views/azb`
- 门户配置、品牌文案、首页说明、默认门户切换已接入：
  - `yuegongbao-ui/src/config/portal.js`
  - `yuegongbao-ui/src/utils/portal.js`
- 只读角色轻视图已接入：
  - `yuegongbao-ui/src/utils/roleView.js`
- 后端和权限模型已支持门户范围字段：
  - `sys_menu.portal_scope`
  - `sys_role.allowed_portal_scope`
  - `sys_role.default_portal_code`
  - `sys_role_menu.portal_scope`

结论：

- 现在不是“要不要拆双前端”的讨论阶段。
- 现在是“如何把同一套后台数据，稳定拆成两个长期业务门户”的实施阶段。

## 3. “七成共性”的正确解释

“七成内容一样”只能解释为下面三层共性，不等于“七成页面继续共用”。

### 3.1 数据共性

必须共后台、共主数据的对象：

- 企业
- 人员
- 设备
- 预警
- 高处作业申报报备
- 工伤事件
- 安责险保单
- 事故预防资金池
- 事故预防项目
- AI 报告与识别结果
- 信用评价底数
- 统计报表底数

### 3.2 业务内核共性

原则上只保留一套能力：

- CRUD
- 状态机
- 上传下载
- 导入导出
- 字典
- 权限校验
- 对外 Stub / 第三方接入
- 汇总聚合接口

### 3.3 页面表达差异

必须分门户承载，不能继续当“共性页面”处理：

- 登录页
- 首页工作台
- 菜单树
- 默认筛选条件
- 摘要卡
- 焦点队列
- 当前对象摘要
- 推荐动作
- 详情抽屉重点
- 报表解释口径

结论：

- `70% 共性 = 共后台 + 共数据 + 共内核`
- `不等于 70% 页面继续一套 CRUD`

## 4. 两个门户的长期定位

### 4.1 粤工保 `ygb`

`ygb` 长期固定为：

- 企业办理工作台
- 人社监管工作台
- 财务整改工作台

页面关键词固定为：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

### 4.2 安责保 `azb`

`azb` 长期固定为：

- 应急治理工作台
- 安责险协同工作台
- 风险处置工作台

页面关键词固定为：

- 风险
- 治理
- 处置
- 时效
- 在途
- 重点对象

## 5. 模块是否必须双视图的判定规则

任意模块上线前，先看下面 6 条：

1. 主要使用角色是否不同。
2. 首要动作是否不同。
3. 首页入口优先级是否不同。
4. 详情页关注重点是否不同。
5. 摘要卡与焦点队列是否不同。
6. 按钮密度和操作深度是否不同。

命中任意 2 条：

- 必须走 `共后台 + 双前端双视图`

只命中 0 到 1 条：

- 才允许继续共页面或只做轻包装

## 6. 按 530.1 的模块拆解定案

### 6.1 `ygb` 独占主链模块

这些模块以后仍然以 `ygb` 为主门户，不进入 `azb` 主工作链：

| 模块 | 当前目录 | 定位 |
| --- | --- | --- |
| 合同备案 | `views/ygb/contract` | 企业用工合规主链 |
| 原始考勤 | `views/ygb/attendanceRaw` | 企业录入与归集主链 |
| 月考勤 | `views/ygb/attendanceMonthly` | 工资发放前置主链 |
| 工资批次 | `views/ygb/salaryBatch` | 财务整改主链 |
| 工资明细 | `views/ygb/salaryDetail` | 财务核对主链 |
| 社保缴费 | `views/ygb/socialPayment` | 参保整改主链 |
| 社保基数比对 | `views/ygb/socialBaseCompare` | 人社整改主链 |
| 个税比对 | `views/ygb/taxCompare` | 财务整改主链 |
| 用工比例 | `views/ygb/employmentRatio` | 专项治理主链 |
| 假外包识别 | `views/ygb/fakeOutsourcing` | 合规复核主链 |
| 新业态人员库 | `views/ygb/newformWorker` | 人社专项监管主链 |
| 职业病监测 | `views/ygb/occupationMonitor` | 人社专项监管主链 |

处理原则：

- 后台继续共数据。
- 前端只在 `ygb` 完整承载。
- `azb` 最多引用结果，不承载完整办理页。

### 6.2 双视图共享模块

这些模块后台共对象，但前端必须双语义落地：

| 模块 | `ygb` 语义 | `azb` 语义 |
| --- | --- | --- |
| 驾驶舱 | 办理总览 | 治理总览 |
| 预警中心 | 办理闭环中心 | 风险处置中心 |
| 预警规则 | 业务规则配置 | 治理规则配置 |
| 单位管理 | 办理主体台账 | 治理对象台账 |
| 人员管理 | 主数据办理 | 风险准入对象 |
| 设备管理 | 接入授权与回执 | 安全治理工作台 |
| 安责险管理 | 参保监管 | 保单治理 |
| 工伤事件 | 申报认定闭环 | 事故协同处置 |
| 预防资金池 | 结算归档 | 风险资金治理 |
| 预防项目 | 执行验收归档 | 项目治理成效 |
| 高处作业申报报备 | 报备留痕与结束登记 | 高危作业治理 |
| AI 监测报告 | 分析归档 | 风险研判 |
| AI 配置 | 评分解释配置 | 治理模型配置 |
| 统计报表 | 办理月报 | 治理月报 |
| 信用评价 | 合规评分 | 风险分层 |
| 漏保清单 | 漏保整改 | 风险对象识别 |

### 6.3 `azb` 主责表达模块

以下模块从后台对象看仍共享，但门户表达应优先按 `azb` 口径演进：

- `views/azb/cockpit`
- `views/azb/device`
- `views/azb/warning`
- `views/azb/heightWorkReport`
- `views/azb/aqInsurance`
- `views/azb/aiReport`
- `views/azb/creditScore`

原因不是复制后台，而是这些模块在 `azb` 的：

- 首要动作
- 摘要重点
- 风险队列
- 详情标签
- 角色权限边界

已经明显不同于 `ygb`。

## 7. 监管重叠内容的拆法

“两个监管部门很多内容重叠”不等于“同一页面继续兼容”。

### 7.1 同对象，不同入口

典型模块：

- 单位管理
- 人员管理
- 预警中心
- 工伤事件
- 高处作业
- AI 报告
- 统计报表

统一处理方式：

- 后台共一套对象。
- `ygb` 从办理链进入。
- `azb` 从风险对象进入。

### 7.2 同数据，不同动作

以高处作业为例：

- `ygb`
  - 先看是否已报备
  - 是否能结束登记
  - 是否缺少完成照片
- `azb`
  - 先看进行中的高危作业
  - 是否证书异常
  - 是否超时未结束
  - 是否位于重点区域

以设备管理为例：

- `ygb`
  - 先看接入授权
  - 先看在线回写是否异常
- `azb`
  - 先看离线
  - 先看锁机失败
  - 先看围栏越界
  - 先看拆除报警

以预警中心为例：

- `ygb`
  - 先看工资、社保、合同、高处作业关联待办
- `azb`
  - 先看红警、重大隐患、重复预警、超时处置

## 8. 按 6.1 的评分挂接定案

### 8.1 `ygb` 的评分解释主链

| 评分域 | 对应模块 | 页面解释重点 |
| --- | --- | --- |
| 工伤预防 | 工伤事件、预防项目、预防资金、统计报表 | 发生率、整改率、归档率 |
| 用工合规 | 合同、考勤、工资、社保、个税、用工比例、假外包 | 异常对象、整改闭环、财务对账 |
| 参保扩面 | 社保、安责险、漏保清单 | 催缴完成率、补缴率、覆盖率 |
| 预警处置 | 预警中心、规则、AI 报告 | 待办量、逾期量、闭环效率 |
| 技术防范 | 高处作业、设备、AI 报告 | 报备留痕、异常压降、现场佐证 |

### 8.2 `azb` 的评分解释主链

| 评分域 | 对应模块 | 页面解释重点 |
| --- | --- | --- |
| 安责险合规 | 安责险、预防资金、预防项目 | 投保覆盖、资金健康、服务执行 |
| 设备安全 | 设备、预警、工伤事件 | 在线率、离线时长、处置时效 |
| 技术防范 | 高处作业、AI 报告、设备 | 在途高危作业、识别异常、风险压降 |
| 隐患整改 | 预警中心、AI 报告、设备 | 重大隐患、重复隐患、超时未闭环 |
| 应急响应 | 驾驶舱、统计报表、区域队列 | 区域态势、重点对象、处置时效 |

### 8.3 固定规则

1. 同一企业在 `ygb`、`azb` 共用一份底数。
2. 同一底数在两个门户必须输出不同解释。
3. 权重与得分点不能写死在页面里，应走配置与聚合层。

## 9. 角色与门户落地规则

| 角色 | 默认门户 | 使用原则 |
| --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 完整企业办理主链 |
| `105 ygb_enterprise_operator` | `ygb` | 录入、修改、提交、结束登记 |
| `106 ygb_hrss_supervisor` | `ygb` | 区域监管、整改闭环、统计复核 |
| `107 ygb_emergency_supervisor` | `azb` | 风险处置、设备治理、高危作业监管 |
| `108 ygb_insurer` | `azb` | 只读安责险、信用评价、报表 |
| `109 ygb_bank` | `azb` | 只读工资风险摘要、信用评价、报表 |

补充规则：

1. `108/109` 统一走轻视图。
2. `ygb` 不承载应急治理主语义。
3. `azb` 不承载企业劳务办理主语义。

## 10. 面向当前代码的直接实施要求

### 10.1 前端目录要求

- `views/ygb/*`
  - 只承接企业办理、人社监管、财务整改主语义
- `views/azb/*`
  - 只承接应急治理、安责险协同、风险处置主语义

### 10.2 后端接口要求

共享模块统一遵循：

- 业务 CRUD 不复制两套
- 补门户聚合接口：
  - `summary`
  - `dashboard`
  - `detail-hint`
  - `focus-queue`

### 10.3 页面结构要求

`ygb` 高频页统一结构：

1. 业务定位
2. 摘要卡
3. 办理焦点
4. 当前选中对象
5. 推荐办理动作
6. 搜索区
7. 工具栏
8. 表格
9. 详情抽屉

`azb` 高频页统一结构：

1. 治理定位
2. 摘要卡
3. 风险队列
4. 当前风险对象
5. 推荐处置动作
6. 风险提示标签
7. 搜索区
8. 工具栏
9. 治理台账
10. 详情抽屉

## 11. 新模块立项前必须回答的 8 个问题

1. 是 `ygb` 独占、`azb` 主责，还是双视图共享。
2. 主数据是否继续共后台。
3. 是否需要 `summary/dashboard/detail-hint` 聚合接口。
4. `ygb` 和 `azb` 的默认入口是否不同。
5. 两个门户的详情重点是否不同。
6. `108/109` 是否需要轻视图。
7. 它挂到 `6.1` 的哪个评分域。
8. 首页是否要加快捷入口或焦点队列。

这 8 个问题没答清楚，不应直接进入页面开发。

## 12. 最终定案

1. 粤工保与安责保应长期保持“一套后台、两个业务门户”。
2. 共性只说明后台可共享，不说明页面可继续共用。
3. 高重叠模块统一落成“同对象、双入口、双摘要、双详情重点”。
4. 后续产品排期、前端派工、后端补接口、测试验收，都按本文先判断模块归属，再进入实施。
