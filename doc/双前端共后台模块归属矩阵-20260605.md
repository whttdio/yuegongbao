# 双前端共后台模块归属矩阵

## 1. 这份文档解决什么问题

这份文档不再讨论“双前端要不要做”，只解决三个执行问题：

1. 同一个业务模块到底归 `ygb`、`azb`，还是双端都要
2. 哪些内容是 `70% 共性`，哪些内容不能再强行共页面
3. 产品、前端、后端、测试在排期时按什么标准拆任务

适用前提固定为：

- 一套后台
- 两个前端门户
- 数据尽量不拆库
- 高度重叠模块走 `共后台 + 双前端语义`

## 2. 先把“七成共性”说清楚

你提到“七成内容都是一样的”，在工程上不能理解成“七成页面完全一样”，而应该固定拆成下面三层：

### 2.1 第一层：数据共性

这部分必须共用，不能拆两套后台：

- 企业主数据
- 人员主数据
- 设备台账
- 预警工单
- 高处作业报备
- 工伤事件
- 安责险保单
- AI 识别结果
- 信用评分结果
- 统计报表底数

### 2.2 第二层：业务内核共性

这部分原则上也只保留一套：

- CRUD
- 状态机
- 导入导出
- 文件上传
- 角色权限底座
- 字典与枚举
- 对外对接 Stub 或正式接口

### 2.3 第三层：页面表达差异

这部分不能再按“共性”处理，必须按门户拆：

- 登录页
- 首页工作台
- 菜单树
- 模块说明
- 摘要卡
- 默认筛选
- 详情抽屉重点
- 快捷入口
- 按钮密度
- 推荐办理路径

结论：

- `70% 共性 = 数据共性 + 业务内核共性 + 可复用组件共性`
- 不能等于 `70% 页面完全共用`

## 3. 一个后台两个前端的最终边界

### 3.1 后台职责

后台只做四类事：

- 统一主数据
- 统一业务状态
- 统一权限校验
- 按门户输出菜单和聚合结果

### 3.2 `ygb` 职责

`ygb` 不是泛后台，而是：

- 企业办理工作台
- 人社监管工作台
- 财务整改工作台

页面核心词应长期固定为：

- 办理
- 归集
- 整改
- 对账
- 归档
- 闭环

### 3.3 `azb` 职责

`azb` 不是 `ygb` 的换皮频道，而是：

- 应急治理工作台
- 安责险协同工作台
- 风险处置工作台

页面核心词应长期固定为：

- 风险
- 治理
- 处置
- 时效
- 在途
- 重点对象

## 4. 模块归属判定标准

任何模块上线前，先按下面 6 条判定是否要双视图：

1. 两边主要使用角色是否不同
2. 两边首要动作是否不同
3. 两边统计口径是否不同
4. 两边首页入口优先级是否不同
5. 两边详情页关注重点是否不同
6. 两边默认按钮密度是否不同

命中任意 2 条：

- 走 `共后台 + 双前端视图`

只命中 0 到 1 条：

- 才允许优先共页面或轻包装

## 6. 监管重叠内容怎么拆

你提到“两个监管部门内容有一大半是重叠的”，这部分应该按“同对象，不同视角”处理。

### 6.1 人社和应急共同关心，但入口不同

这类模块：

- 人员管理
- 单位管理
- 预警中心
- 工伤事件
- 高处作业
- 统计报表
- AI 报告

拆法：

- 后台同一套对象
- `ygb` 首页从“办理链”进入
- `azb` 首页从“风险对象”进入

### 6.2 两边都看同一数据，但行动方式不同

示例：

- 高处作业
  - `ygb`：企业管理员先看是否已报备、是否可结束、是否要补照片
  - `azb`：应急监管先看进行中、异常证书、重点区域、是否超时未结束
- 设备管理
  - `ygb`：企业侧先看授权、接入、在线回写异常
  - `azb`：应急侧先看离线、拆除、锁机失败、围栏越界
- 预警中心
  - `ygb`：先看与工资、社保、合同、高处作业关联的待处理事项
  - `azb`：先看红警、重大隐患、处置时效、重复预警

结论：

- 重叠不代表入口一样
- 重叠不代表详情一样
- 重叠不代表按钮一样

## 7. 从用户高频使用角度再拆一遍

### 7.1 企业管理员

高频路径：

- 合同
- 考勤
- 工资
- 社保
- 个税
- 预警
- 高处作业

需要的不是风险大屏，而是：

- 哪些事项卡住了
- 哪些对象要补资料
- 哪些事项今天必须办完

### 7.2 工地负责人

高频路径：

- 人员
- 设备
- 高处作业
- 预警

需要的是：

- 当前现场谁有风险
- 哪台设备异常
- 哪个作业还没结束留痕

### 7.3 操作员

高频路径：

- 录入
- 导入
- 修改
- 重提

需要的是：

- 少噪音
- 强校验
- 清晰反馈

### 7.4 财务

高频路径：

- 工资
- 社保
- 个税
- 预防资金
- 报表

需要的是：

- 异常原因
- 对账出口
- 批量导出

### 7.5 人社监管员

高频路径：

- 合规链摘要
- 漏保整改
- 工伤预防
- 统计报表

需要的是：

- 区域异常对象
- 整改闭环率
- 月度归档

### 7.6 应急监管员

高频路径：

- 驾驶舱
- 设备
- 预警
- 高处作业
- AI 报告

需要的是：

- 重大风险对象
- 实时处置队列
- 超时未闭环事项

### 7.7 保险公司与银行

高频路径：

- 安责险
- 预防资金
- 信用评价
- 统计报表

需要的是：

- 只读摘要
- 快速下钻
- 不参与复杂维护

## 8. 对当前仓库的直接落地要求

按现有代码结构，后续不要再争论目录怎么拆，直接遵循：

- `yuegongbao-ui/src/views/ygb/*`
  - 承接企业办理、人社监管、财务整改主链
- `yuegongbao-ui/src/views/azb/*`
  - 承接应急治理、安责险协同、风险处置主链
- 后端继续保留一套业务域
  - 通过 `summary/dashboard` 做门户差异化聚合

SQL 和权限固定围绕下面四个字段走：

- `sys_menu.portal_scope`
- `sys_role.allowed_portal_scope`
- `sys_role.default_portal_code`
- `sys_role_menu.portal_scope`

## 9. 这份矩阵怎么用

产品排期时先填 6 个字段：

1. 模块名
2. 是否共后台
3. `ygb` 是否主操作
4. `azb` 是否主操作
5. 页面语义关键词
6. 角色优先级

开发派工时再补 5 个字段：

1. 是否要补 `summary/dashboard`
2. 是否需要双详情抽屉重点
3. 是否需要只读轻视图
4. 是否需要首页快捷入口
5. 是否需要角色队列

测试验收时固定检查：

1. 菜单是否在正确门户显示
2. 按钮是否按角色收口
3. 同一对象在两个门户的解释是否明显不同
4. 数据是否仍然共后台同口径

## 10. 最终结论

1. 一个后台两个前端是对的，而且当前仓库已经具备继续推进的底座。
2. `70% 共性` 应理解为 `共数据 + 共内核 + 共组件`，不能理解为 `共页面`。
3. 人社与应急有大面积监管重叠，但应落成“同对象、双视角、双入口、双详情重点”。
4. 未来所有新模块，都先按这份矩阵判定归属，再决定是否需要双前端同步开发。
