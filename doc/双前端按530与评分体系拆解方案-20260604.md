# 双前端按 530.1 与评分体系 6.1 拆解方案

## 1. 结论先行

粤工保和安责保不应继续理解成“一套页面换两套登录皮肤”，而应理解成：

- 一套后台底座：主数据、业务表、状态机、权限底座统一
- 两套长期独立前端工作台：
  - `ygb`：企业办理 + 人社监管
  - `azb`：风险治理 + 应急监管 + 保险协同

核心判断来自两份文档：

- `粤工保开发需求分析说明书（530.1版）`
- `粤工保与安责保平台评分体系细化得分点6.1`

两份文档共同指向三个事实：

1. 企业、人员、设备、预警、高处作业、AI 等底层数据必须打通，不能拆成两套主表。
2. 粤工保和安责保的考核口径、首页优先级、角色高频动作并不相同。
3. 只要用户动作和统计口径不同，就不应继续共用同一套前端页面表达。

## 2. 拆解原则

### 2.1 后端只保留一套

统一保留：

- 企业主数据
- 人员主数据
- 设备台账与事件
- 预警事件与工单闭环
- 高处作业报备
- AI 报告原始结果
- 安责险、工伤、预防项目、预防资金
- 角色、菜单、按钮权限

统一方式：

- 请求头继续使用 `X-Portal-Code`
- 菜单和按钮继续使用 `portal_scope`
- 共性模块前端语义拆开：
  - `ygb/heightWorkReport` = 高处作业报备办理台账
  - `azb/heightWorkReport` = 高危作业治理台账
- 聚合能力优先补 `summary/dashboard`，不复制 CRUD

### 2.2 前端必须拆成两个工作台

`ygb` 和 `azb` 必须至少在以下维度独立：

- 登录页品牌和引导语
- 首页与工作台
- 默认快捷入口
- 驾驶舱与摘要卡片
- 模块顶部业务说明
- 列表默认筛选项
- 详情页摘要顺序
- 只读角色与办理角色的入口密度

### 2.3 判定一个模块是否必须双视图

满足以下任意 2 条，就按“双前端独立视图”处理：

1. 两边核心使用角色不同
2. 两边首要动作不同
3. 两边统计口径不同
4. 两边首页入口优先级不同

## 3. 模块拆解矩阵

### 3.1 仅 `ygb` 完整呈现的模块

- 合同备案
- 考勤上报
- 考勤归集
- 工资批次
- 工资明细
- 社保缴费 / 社保比对
- 个税比对
- 用工比例
- 假外包识别
- 新业态人员库

原因：

- 这些模块服务的是企业办事链和人社监管链。
- 安责保会引用结果，但不应承载这些办理页面。

### 3.2 后台共用、双前端双视图的模块

- 单位管理
- 人员管理
- 预警中心
- 预警规则
- 设备管理
- 安责险管理
- 工伤事件
- 事故预防资金池
- 预防项目
- 高处作业申报报备
- AI 监测报告
- AI 模型配置
- 统计报表
- 信用评价
- 漏保清单
- 驾驶舱

原则：

- 表结构、接口、状态机统一
- `ygb/azb` 前端视图分别设计
- 门户差异主要落在摘要、筛选、默认动作和页面语言
- 已落地示例：
  - `ygb/enterprise` 走“企业主数据办理台账”，重点是承接人员、合同、考勤、工资链路
  - `ygb/person` 走“人员主数据办理台账”，重点是承接合同、考勤、工资和参保核对链路
  - `ygb/warning` 走“联动预警办理闭环”，重点是社保、个税、扩面和专项治理异常的催办与归档
  - `azb/enterprise` 走“治理对象台账”，重点是同步异常、停用企业和现场治理范围
  - `azb/person` 走“准入风险台账”，重点是证书临期、未参保和现场授权准备
  - `azb/warning` 走“现场风险处置中心”，重点是红警、设备/AI 和应急闭环压降

### 3.3 `azb` 重点强化模块

以下模块即使后端不拆，也必须长期按 `azb` 独立视图演进：

- 驾驶舱
- 设备管理
- 预警中心
- 高处作业申报报备
- 安责险管理
- AI 监测报告
- 事故预防资金池
- 预防项目

原因：

- 它们直接对应评分体系中的风险识别、现场治理、保险协同、应急处置。
- 用户第一诉求不是录入数据，而是快速识别重点对象并闭环处置。

## 4. 角色视角的真实工作台

### 4.1 `ygb` 主服务角色

- `104 ygb_enterprise_admin`
- `105 ygb_enterprise_operator`
- `106 ygb_hrss_supervisor`
- 企业财务 / 经办类账号

首页应该优先呈现：

- 待备案合同
- 待归集考勤
- 待生成工资明细批次
- 社保 / 个税异常对象
- 预警闭环
- 当前代码已进一步落地为三组真实首页队列：
  - 过程链：`待备案合同 / 未归集考勤 / 待生成工资明细 / 进行中高处作业`
  - 财务链：`发放失败工资明细 / 社保欠费 / 社保基数异常 / 个税异常`
  - 监管链：`待核查漏保名单 / 待处置预警 / 待生成月报`

### 4.2 `azb` 主服务角色

- `107 ygb_emergency_supervisor`
- `108 ygb_insurer`
- `109 ygb_bank`
- 企业现场负责人
- 设备管理员

首页应该优先呈现：

- 红警待处置
- 待授权设备 / 异常设备
- 进行中高处作业
- 风险保单
- 高风险 AI 对象
- 当前代码已按角色继续收敛首页队列：
  - `ygb_emergency_supervisor`：`红警待处置 / 待授权设备 / 进行中高处作业 + 风险保单 / 低余额资金池 / 红码信用对象 / 可查看区域报表`
  - `ygb_insurer`：只保留 `风险保单 / 低余额资金池 / 红码信用对象 / 可查看区域报表`
  - `ygb_bank`：只保留 `红码信用对象 / 可查看区域报表`

### 4.3 只读角色策略

`108/109` 不适合继续看到复杂录入页。

应优先保留：

- 摘要卡
- 详情页
- 导出
- 报表

应尽量收口：

- 新增
- 修改
- 结束
- 批量导入
- 复杂工作流入口

## 5. 页面与接口边界

### 5.1 页面负责什么

页面负责：

- 门户语言
- 角色入口
- 摘要卡片
- 重点对象队列
- 详情页侧重点

### 5.2 接口负责什么

接口负责：

- 统一 CRUD
- 统一主数据
- 统一状态机
- 门户级 `summary/dashboard`
- 按门户返回菜单和权限

### 5.3 不再做什么

后续不建议继续：

- 用 `azb` 包一层 `ygb` 页面长期凑合
- 用列表第一页拼首页摘要
- 同一页面同时照顾企业办理和应急治理两套语义

## 7. 验收标准

1. 同一账号进入 `ygb` 和 `azb`，看到的是两套明显不同的工作台。
2. 共性模块不复制后台表和核心接口。
3. `ygb` 首页优先解决办理闭环，`azb` 首页优先解决风险闭环。
4. 保险、银行等只读角色不再被复杂录入入口干扰。
5. 后续新模块能先按本方案判断：共后台、单门户还是双门户双视图。
