# 双前端实施批次与派工验收单

## 1. 使用方式

这份文档不再讨论“双前端要不要做”，只服务四件事：

1. 产品拆需求
2. 前后端排批次
3. 测试做验收
4. 管理者判断本周是否真正推进

适用前提固定为：

- 仓库仍是 `一套后台`
- 门户固定为 `ygb` 与 `azb`
- 不新建第二套业务库
- 不复制同一对象的两套 CRUD

## 2. 实施总原则

### 2.1 后端原则

- 统一主数据
- 统一 CRUD
- 统一状态机
- 优先补 `summary/dashboard`
- 权限走 `portal_scope + role + perm`

### 2.2 前端原则

- `ygb` 与 `azb` 固定为两套工作台
- 共享模块必须拆 `views/ygb` 与 `views/azb`
- 不再让一个页面兼顾两套门户语义
- 高频页必须支持“摘要 + 焦点 + 当前对象 + 详情联动”

### 2.3 测试原则

- 先验角色入口，再验页面闭环
- 先验摘要是否来自后端，再验列表与抽屉联动
- 先验只读角色权限收口，再验操作角色闭环

## 3. 当前仓库已经具备的底座

已落地的能力：

- 登录页门户品牌区分
- `X-Portal-Code`
- `sys_menu.portal_scope`
- `sys_role.allowed_portal_scope`
- `sys_role.default_portal_code`
- `sys_role_menu.portal_scope`
- 角色跨门户自动归位
- `ygb` / `azb` 工作台样式底座

所以后续重点不再是框架搭建，而是剩余模块的工作台化和评分口径化。

## 4. 四个执行批次

## 4.1 P0 批次：补齐 `ygb` 剩余企业高频主链

### 目标

把仍偏基础 CRUD 的人社/财务/企业高频页面，升级成真正能高频使用的办理台账。

### 页面清单

| 页面 | 当前问题 | 本批动作 | 后端补充 |
| --- | --- | --- | --- |
| `ygb/taxCompare` | 仍偏基础列表 | 改成个税比对整改台账 | 补 `summary` |
| `ygb/employmentRatio` | 缺少整改焦点 | 改成用工比例合规台账 | 补 `summary` |
| `ygb/fakeOutsourcing` | 缺少疑似对象复核路径 | 改成假外包识别复核台账 | 补 `summary` |
| `ygb/newformWorker` | 缺少重点对象摘要 | 改成新业态人员监管台账 | 补 `summary` |
| `ygb/occupationMonitor` | 缺少区域聚合与异常承接 | 改成职业病监测台账 | 补 `summary` |
| `ygb/cockpit` | 仍需强化待办与整改入口 | 改成企业办理首页工作台 | 补首页聚合接口 |

### 前端固定结构

1. 顶部业务定位
2. 摘要卡
3. 办理焦点
4. 当前选中对象
5. 办理路径
6. 搜索区
7. 工具栏
8. 台账表格
9. 详情抽屉

### 验收口径

1. 企业管理员进入页面，3 秒内能知道当前待处理对象是谁
2. 摘要不从当前分页临时拼装，必须来自后端聚合
3. 行点击能联动当前对象和详情抽屉
4. `vite build --mode ygb` 通过

## 4.2 P1 批次：补齐 `azb` 风险治理主链

### 目标

把安责保从“独立入口”继续升级成“多角色治理工作台”，重点解决应急、保险、银行看到同页信息过载的问题。

### 页面清单

| 页面 | 本批动作 | 核心角色 |
| --- | --- | --- |
| `azb/cockpit` | 首页队列按 `107/108/109` 分层 | 应急/保险/银行 |
| `azb/warning` | 角色化焦点队列、当前对象、详情重点 | 应急/保险/银行 |
| `azb/device` | 工地负责人、设备管理员、只读协同分轻重视图 | 应急/企业/保险 |
| `azb/aqInsurance` | 强化只读协同视图和保单风险摘要 | 保险/应急 |
| `azb/heightWorkReport` | 强化在途作业、凭证、结束佐证优先级 | 应急/企业 |
| `azb/aiReport` | 强化高风险对象、压降趋势、时效 | 应急/保险 |

### 后端补充

| 能力 | 动作 |
| --- | --- |
| 首页聚合 | `azb` 首页按 `107/108/109` 返回不同焦点队列 |
| 评分映射 | 先补 `AQ/C/F/H/E` 所需聚合字段 |
| 权限兜底 | 对导入、维护、处置、设备指令类接口做只读角色校验 |

### 验收口径

1. `107` 看得到治理闭环入口
2. `108/109` 看不到复杂录入、维护、指令按钮
3. 详情重点突出“风险等级、处置状态、剩余时效”
4. `vite build --mode azb` 通过

## 4.3 P2 批次：把 `530.1` 数据正式接入 `6.1` 评分

### 目标

让双前端不只是双工作台，还能按不同监管口径输出不同评分结果和解读。

### 后端任务

| 能力 | 任务 |
| --- | --- |
| 评分配置 | 增加维度、得分点、权重、目标值配置 |
| ETL 聚合 | 按月聚合工伤、参保、设备、预警、技术防范指标 |
| 评分服务 | 输出企业分、区域分、维度分、得分点明细 |
| 报表联动 | AI 报告、统计报表、信用评价复用评分结果 |

### 前端任务

| 门户 | 任务 |
| --- | --- |
| `ygb` | 首页与报表突出工伤预防、用工合规、扩面减损、预警闭环 |
| `azb` | 首页与报表突出安责险、设备在线、技术防范、隐患整改、应急响应 |

### 验收口径

1. 同一企业在 `ygb` 与 `azb` 可看到不同维度排序和解读
2. 得分结果可追溯到具体得分点
3. 权重调整不需要改代码逻辑

## 4.4 P3 批次：完成双门户首页和角色入口收口

### 目标

把“登录页不同”升级为“登录后首屏工作方式不同”。

### 任务清单

| 类型 | 动作 |
| --- | --- |
| 首页工作台 | `ygb` 强调待办、整改、财务闭环；`azb` 强调红警、在途高危、设备异常、治理时效 |
| 默认入口 | `104/105/106` 固定走 `ygb` 首页队列；`107/108/109` 固定走 `azb` 首页队列 |
| 快捷入口 | `ygb` 放合同、考勤、工资、高处作业；`azb` 放驾驶舱、设备、预警、高处作业 |
| 轻视图 | `108/109` 首页只保留摘要、报表、详情跳转，不进入复杂维护页 |

### 验收口径

1. 不同角色登录后的首屏重点对象明显不同
2. `ygb` 首屏不会被安责保治理语义污染
3. `azb` 首屏不会出现企业劳务办理主链入口

## 5. 按模块类型的开发规则

## 5.1 `ygb` 独占模块

适用模块：

- 合同
- 考勤
- 工资
- 社保
- 个税
- 用工比例
- 假外包
- 新业态
- 职业病

统一规则：

- 继续共后台
- 页面只在 `ygb` 完整开放
- 必须补 `summary`
- 首页待办要沉淀成聚合接口

## 5.2 双视图共享模块

适用模块：

- 单位
- 人员
- 预警
- 设备
- 安责险
- 工伤
- 预防资金
- 预防项目
- 高处作业
- AI 报告
- 统计报表
- 信用评价
- 漏保清单
- 驾驶舱

统一规则：

- CRUD 不复制
- `summary/dashboard` 按门户拆口径
- 详情允许补门户字段，但不复制主表
- 页面必须拆 `views/ygb/*` 与 `views/azb/*`

页面联调时固定检查四项：

1. 是否已有门户聚合接口
2. 是否已有当前对象联动
3. 是否已有只读角色按钮收口
4. 是否已有 `ygb/azb` 两套详情重点

## 5.3 只读协同角色模块

适用角色：

- `108 ygb_insurer`
- `109 ygb_bank`

统一规则：

- 前端必须提供轻视图
- 隐藏新增、修改、结束、同步、指令、启停、版本维护
- 后端继续做接口级权限校验

建议统一沉淀一个只读判定层：

- 命中 `ygb_insurer`、`ygb_bank` 时默认走 `read-only-lite`

## 6. 派工模板

任何双前端共享模块，都按下面模板派工。

### 产品任务

- 明确模块归属：`ygb` 独占 / 双视图共享 / `azb` 治理优先
- 明确两端摘要卡差异
- 明确两端默认筛选差异
- 明确两端详情关注点差异
- 明确只读角色可见边界

### 后端任务

- 盘点是否已有统一 CRUD
- 新增或补齐 `summary/dashboard`
- 检查 `portal_scope`
- 检查接口权限是否符合角色矩阵

### 前端任务

- 建立或升级 `views/ygb/*` / `views/azb/*`
- 补“摘要 + 焦点 + 当前对象 + 详情联动”
- 做只读角色轻视图收口
- 统一门户语义文案

### 测试任务

- 角色登录验证
- 菜单显隐验证
- 摘要接口验证
- 表格与详情联动验证
- 操作权限验证
- 构建验证

## 7. 交付物要求

每一批次结束时，至少交付：

1. 代码改动
2. 文档回写
3. 构建结果
4. 角色验收截图或记录

禁止只交“页面换标题”或“顶部加 Banner”的伪双前端成果。

## 8. 本周推荐执行顺序

按当前仓库成熟度，建议顺序固定为：

1. 先完成 `ygb` 剩余高频页工作台化
2. 再完成 `azb` 治理主链角色化
3. 再接评分体系聚合与解释
4. 最后统一收口双门户首页与默认入口

这样排的原因很直接：

- 先把高频页做成真正能用
- 再把双前端做成真正有差异
- 最后再上评分和首页汇总，不会出现“首页很漂亮，底层还是 CRUD”的空转
