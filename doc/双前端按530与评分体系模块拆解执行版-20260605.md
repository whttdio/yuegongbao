# 双前端按 530.1 与评分体系 6.1 模块拆解执行版

## 1. 目的

这份文档用于把你描述的现状固定成工程边界：

- 一个后台
- 两个前端门户
- 两套登录入口和首页语义
- 七成共性只落在数据与业务内核，不再理解成七成页面完全一样

输入依据固定为两份业务文档：

- `粤工保开发需求分析说明书（530.1版）`
- `粤工保与安责保平台评分体系细化得分点6.1`

## 2. 先给结论

粤工保和安责保的正确拆法不是“两套后台”，也不是“同一页换两套登录皮肤”，而是：

- 后端共一套主数据、业务表、状态机、权限底座
- `ygb` 作为 `企业办理 + 人社监管 + 财务整改` 工作台
- `azb` 作为 `应急治理 + 安责险协同 + 风险处置` 工作台
- 共性模块继续共 CRUD 和主表
- 门户差异集中在登录页、首页、摘要卡、默认筛选、详情重点、按钮密度、推荐路径

## 3. “七成共性”在工程上的真实含义

### 3.1 数据共性

必须共用，不能拆库：

- 企业主数据
- 人员主数据
- 设备台账
- 预警工单
- 高处作业报备
- 工伤事件
- 安责险保单
- AI 识别结果
- 信用评价结果
- 统计报表底数

### 3.2 业务内核共性

原则上也只保留一套：

- CRUD
- 状态机
- 导入导出
- 文件上传
- 字典和枚举
- 权限校验
- 外部系统 Stub / 正式接口

### 3.3 页面表达差异

这部分不能再按“共性”处理，必须按门户拆：

- 登录页
- 首页工作台
- 菜单树
- 模块说明
- 摘要卡
- 默认筛选
- 详情抽屉重点
- 快捷入口
- 按钮密度
- 推荐办理路径

结论只有一句：

- `共后台` 可以很高
- `共页面` 不能再高

## 5. 模块是否需要双视图的判定标准

一个模块满足下列任意 2 条，就必须拆成 `views/ygb` 和 `views/azb` 两套工作台：

1. 主要使用角色不同
2. 首要动作不同
3. 统计口径不同
4. 首页入口优先级不同
5. 详情页关注重点不同
6. 默认摘要卡、默认筛选、默认按钮密度不同

## 7. 两个监管部门内容重叠时怎么拆

### 7.1 同对象，不同入口

这类模块：

- 单位管理
- 人员管理
- 预警中心
- 工伤事件
- 高处作业
- 统计报表
- AI 报告

统一处理方式：

- 后台共对象
- `ygb` 从办理链进入
- `azb` 从风险对象进入

### 7.2 同数据，不同行动

典型例子：

- 高处作业
  - `ygb` 先看是否已报备、是否可结束、是否缺照片
  - `azb` 先看进行中、异常证书、重点区域、超时未结束
- 设备管理
  - `ygb` 先看授权、接入、在线回写异常
  - `azb` 先看离线、越界、锁机失败、AI 异常
- 预警中心
  - `ygb` 先看与合同、工资、社保、高处作业关联的待处理事项
  - `azb` 先看红警、重大隐患、重复预警、处置时效

结论：

- 重叠不代表入口一样
- 重叠不代表详情一样
- 重叠不代表按钮一样

5. `108/109` 是否需要轻视图

### 7.1 重度使用者视角下的真实分工

从长期高频使用看，至少要按下面几类人去组织页面，而不是只按模块名组织：

#### `ygb` 重点用户

- 企业管理员
  - 关注合同、考勤、工资、社保、个税、预警、高处作业的闭环进度
- 工地负责人
  - 关注现场人员、预警、在途高处作业、作业结束留痕
- 操作员
  - 关注录入、导入、修正、退回重提
- 财务
  - 关注工资发放、专户监管、比对异常、导出对账
- 人社监管员
  - 关注区域异常企业、整改率、漏保对象、月度归档

#### `azb` 重点用户

- 应急监管员
  - 关注红警对象、设备异常、高危作业、区域处置时效
- 保险公司
  - 关注投保覆盖、保单风险、预防资金、事故和信用
- 银行
  - 关注工资风险摘要、企业信用、统计报表
- 工地安全负责人
  - 关注当前风险对象、现场联动、结束佐证、重复隐患
- 设备管理员
  - 关注设备在线率、告警、停机、复位、巡检结果

这也是为什么同一后台不能再用同一张通用 CRUD 页面承接所有角色。

## 8. 页面表达规则

### 8.1 `ygb` 统一页面表达

统一结构：

1. 顶部业务定位
2. 摘要卡
3. 办理承接焦点
4. 当前选中对象概览
5. 办理路径
6. 搜索区

统一目标：

- 让企业管理员、经办、财务一眼看到“下一步要办什么”
- 摘要不要从当前分页表格临时拼出来，必须来自后端聚合

### 8.2 `azb` 统一页面表达

统一结构：

1. 顶部治理定位
2. 摘要卡
3. 当前筛选结果重点
4. 当前选中对象风险概览
5. 风险提示
6. 搜索区
7. 工具栏
8. 治理台账
9. 详情抽屉

统一目标：

- 让应急、保险、银行、工地负责人一眼看到“当前风险对象是谁、是否需要处置”

### 8.3 两个门户的页面语言必须长期分开

`ygb` 页面文案统一偏：

- 办理
- 归集
- 整改
- 对账
- 归档
- 待我处理

`azb` 页面文案统一偏：

- 风险
- 治理
- 处置
- 闭环
- 时效
- 当前重点对象

如果一个页面同时出现两套语义，基本说明这个页面还没拆干净。

## 10. 最终拆解结论

1. 双前端继续成立，而且已经不是概念方案，而是现有仓库的真实实施路径。
2. 后端不要拆成两套业务库，继续走“一套 CRUD + 门户级 summary/dashboard”的方式。
3. `ygb` 承接企业办理和人社监管主链，`azb` 承接风险治理和应急协同主链。
4. 真正需要持续投入的不是“复制页面”，而是把剩余页面从表格式 CRUD 升级成按角色工作的台账页。
