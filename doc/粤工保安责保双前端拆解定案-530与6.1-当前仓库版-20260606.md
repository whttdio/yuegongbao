# 粤工保 / 安责保双前端拆解定案（530 与 6.1，当前仓库版）
日期：2026-06-06

## 1. 定案结论

当前系统应固定为以下长期结构：

- 一套后台
- 两个前端入口
- 两套登录页
- 两套首页工作台
- 一套业务对象主数据
- 一套核心业务接口
- 一套权限底座，按门户和角色做显隐与动作收口

这不是“同一个系统换两个标题”，而是：

- `ygb` 负责企业办理、人社监管、财务整改、业务闭环
- `azb` 负责应急监管、安责险协同、设备安全、风险治理
- 后台只保留一套对象和一套状态机
- 前端按不同监管语义重组入口、摘要、详情重点、推荐动作

结合 `粤工保开发需求分析说明书（530.1版）` 与 `粤工保与安责保平台评分体系细化得分点6.1`，本次拆解的硬结论如下：

1. 七成共性，说明后台必须共用，不说明页面必须共用。
2. 八成能力偏粤工保，说明 `ygb` 是主业务门户，`azb` 是治理与监管门户，不是五五拆分。
3. 两个监管部门的大量重叠能力，正确做法是“同对象、双门户、双摘要、双工作台”，不是复制第二套表和第二套接口。

## 2. 当前仓库已具备的双门户基础

当前仓库不是从零开始，以下基础已经存在：

- 双登录入口
  - `/login/ygb`
  - `/login/azb`
- 门户配置
  - `yuegongbao-ui/src/config/portal.js`
- 门户路由与跳转
  - `yuegongbao-ui/src/router/index.js`
  - `yuegongbao-ui/src/utils/portal.js`
  - `yuegongbao-ui/src/permission.js`
- 门户菜单过滤
  - `yuegongbao-ui/src/store/modules/permission.js`
- 双前端页面目录
  - `yuegongbao-ui/src/views/ygb`
  - `yuegongbao-ui/src/views/azb`
- 首页工作台与角色工作剧本
  - `yuegongbao-ui/src/views/index.vue`
  - `yuegongbao-ui/src/views/homeWorkbenchConfig.js`

这意味着本次工作重点不再是“要不要双前端”，而是“哪些模块继续共逻辑双外壳，哪些模块只保留在 ygb，哪些模块在 azb 强化治理表达”。

## 3. 两个前端各自承担什么

### 3.1 粤工保 `ygb`

长期定位：

- 企业管理员工作台
- 企业经办工作台
- 财务整改工作台
- 人社监管工作台

首页和模块语义应围绕以下动作组织：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

`ygb` 是 530.1 主业务链的主承载端，重点模块包括：

- 合同备案
- 考勤采集与归集
- 工资批次与工资明细
- 社保缴费与社保基数比对
- 个税比对
- 用工比例、假外包、新业态、职业病等专项治理
- 工伤预防与扩面减损
- 企业基础管理
- 月报、统计、归档

### 3.2 安责保 `azb`

长期定位：

- 应急监管工作台
- 安责险协同工作台
- 风险治理工作台
- 现场安全工作台

首页和模块语义应围绕以下动作组织：

- 风险
- 处置
- 时效
- 在途
- 重点对象
- 区域治理

`azb` 是 6.1 评分与治理解释链的主承载端，重点模块包括：

- 安责险管理
- 设备安全治理
- 技术防范
- 高处作业申报报备
- AI 风险识别与 AI 报告
- 预警中心
- 事故预防资金 / 项目
- 区域态势、治理成效、评分解释

## 4. 一套后台必须共用的边界

以下对象必须保持单源，不允许按门户再造第二套业务表：

- 企业
- 人员
- 合同
- 考勤
- 工资
- 社保
- 税务
- 预警
- 预警规则
- 设备
- 高处作业申报报备
- 工伤事件
- 安责险保单
- 事故预防项目
- 事故预防资金
- AI 原始事件 / AI 报告 / AI 配置
- 信用评分底数
- 统计报表底数
- 首页 / 驾驶舱聚合底数
- 角色 / 菜单 / 门户范围

共享后台的正确含义是：

- 一套业务表
- 一套状态机
- 一套核心接口
- 一套校验规则
- 一套导入导出主逻辑

共享后台不等于：

- 共用同一套首页
- 共用同一套工作台文案
- 共用同一套详情结构
- 共用同一套操作优先级

## 5. 模块拆解定案

### 5.1 只在 `ygb` 完整承载的模块

这些模块属于企业办理主链，不建议在 `azb` 再做完整办理页：

- `contract`
- `attendanceRaw`
- `attendanceMonthly`
- `salaryBatch`
- `salaryDetail`
- `socialPayment`
- `socialBaseCompare`
- `taxCompare`
- `employmentRatio`
- `fakeOutsourcing`
- `newformWorker`
- `occupationMonitor`

`azb` 如确需使用这些数据，只允许引用摘要结果、风险结论、评分解释，不再承接原始办理流程。

### 5.2 必须共后台 + 双外壳的共享模块

这些模块后端共用，但前端必须按双门户分开表达：

- `home`
- `cockpit`
- `enterprise`
- `person`
- `warning`
- `warningRule`
- `device`
- `aqInsurance`
- `preventionFund`
- `preventionProject`
- `injuryEvent`
- `heightWorkReport`
- `aiReport`
- `aiReportConfig`
- `creditScore`
- `statReport`
- `uninsuredList`

这类模块必须遵守统一模式：

- 共用 `useXxxPage.js` 或共用 API / 业务装配
- `src/views/ygb/<module>/index.vue` 承载粤工保语义
- `src/views/azb/<module>/index.vue` 承载安责保语义
- 同对象在两端都可查，但首页摘要、详情强调字段、推荐动作不同

### 5.3 `azb` 主责强化的模块

以下模块虽然共后台，但前端表达必须明显偏向 `azb`：

- 安责险管理
- 设备管理
- 技术防范
- 高处作业申报报备
- AI 风险识别 / AI 报告
- 区域风险驾驶舱
- 预警处置时效
- 事故预防资金 / 项目
- 6.1 评分解释视图

这些模块在 `azb` 的表达要比 `ygb` 更强调：

- 当前风险等级
- 重点对象队列
- 在途处置
- 超时未闭环
- 区域分布
- 治理效果

## 6. 530.1 与 6.1 的挂接原则

### 6.1 `ygb` 的解释口径

`ygb` 对同一底数的解释应围绕“业务办理价值”展开：

- 劳务合规
  - 合同、考勤、工资、社保、个税、用工比例、假外包
- 工伤预防
  - 工伤事件、预防项目、预防资金
- 扩面减损
  - 漏保、参保覆盖、催缴与补缴
- 预警闭环
  - 预警中心、规则、AI 报告
- 技术防范留痕
  - 高处作业、设备接入、AI 识别结果

页面应突出：

- 当前异常对象
- 办理堵点
- 整改完成率
- 月报归档结果

### 6.2 `azb` 的解释口径

`azb` 对同一底数的解释应围绕“治理成效”展开：

- 安责险合规
  - 投保覆盖、保单有效、预防资金健康度
- 设备安全
  - 在线率、离线时长、授权状态、处置时效
- 技术防范
  - 高危作业在途、证书异常、AI 风险压降
- 隐患整改
  - 重大隐患、重复隐患、超时未闭环
- 应急响应
  - 区域态势、重点对象、协同处置效果

页面应突出：

- 风险对象队列
- 当前风险等级
- 处置时效
- 区域治理热点

### 6.3 固定挂接原则

1. 同一企业在 `ygb` 与 `azb` 共用同一底数。
2. 同一底数在两端必须输出不同的解释顺序。
3. 评分权重优先走配置，不写死在前端页面。
4. 评分说明、指标解释、钻取入口允许门户差异化。

## 7. 角色与门户归属定案

| 角色 | 默认门户 | 长期定位 | 页面重点 |
| --- | --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 企业管理员 | 合同、考勤、工资、社保、预警、高处作业 |
| `105 ygb_enterprise_operator` | `ygb` | 企业经办员 | 录入、导入、修改、提交、结束登记 |
| `106 ygb_hrss_supervisor` | `ygb` | 人社监管员 | 劳务合规、扩面减损、工伤预防、区域监管 |
| `107 ygb_emergency_supervisor` | `azb` | 应急监管员 | 红警、设备、高危作业、AI 风险、处置时效 |
| `108 ygb_insurer` | `azb` | 保险公司 | 保单风险、预防资金、信用评价、统计报表 |
| `109 ygb_bank` | `azb` | 银行 | 工资风险摘要、信用评价、统计报表 |

固定规则：

1. `104/105/106` 默认进入 `ygb`。
2. `107/108/109` 默认进入 `azb`。
3. `108/109` 保持轻视图，只保留摘要、详情、导出、报表。
4. 企业角色允许访问双门户时，`ygb` 仍为主入口。
5. `azb` 只承接治理与监管表达，不承接完整劳务办理流程。

## 8. 前端实施边界

目录规范固定为：

- 共享业务逻辑
  - `src/views/<module>/useXxxPage.js`
- 粤工保外壳
  - `src/views/ygb/<module>/index.vue`
- 安责保外壳
  - `src/views/azb/<module>/index.vue`

共享层负责：

- 数据查询
- 列表加载
- 摘要加载
- 详情加载
- 导入导出
- 状态处理
- 公共字典
- 只读动作判断

外壳层负责：

- 门户文案
- 首屏摘要
- 焦点队列
- 当前对象解读
- 推荐动作排序
- 角色提示

禁止做法：

- 复制第二套后台表
- 复制第二套 API
- `azb` 直接套 `ygb` 页面只改标题
- 把大量业务逻辑重新堆回两个页面外壳

## 9. 当前仓库落地状态判断

按当前代码，以下判断成立：

- 双登录页已存在
- 双门户配置已存在
- 门户菜单过滤已存在
- 默认门户 / 错门户回跳已存在
- 首页工作台已开始按角色与门户区分
- 多个共享模块已进入“共逻辑 + 双外壳”形态

当前最值得继续推进的不是重新争论架构，而是继续做这三件事：

1. 把剩余共享模块彻底去同质化，尤其是详情页与推荐动作。
2. 把 `530.1` 与 `6.1` 的指标解释正式挂接到双门户工作台与报表页。
3. 把首页重点队列、对象台账、详情回跳做成真实业务闭环，而不是普通 CRUD 页面集合。

## 10. 研发结论

后续研发统一按以下口径执行：

- 后台继续坚持单套
- 前端继续坚持双门户
- 共性能力共逻辑，不共首屏表达
- 企业办理主链收口到 `ygb`
- 治理与监管主链强化到 `azb`
- 同一对象双视图，不双建模

这份定案可直接作为产品、前端、后端、测试共同的拆解边界基线。
