# 粤工保 / 安责保双前端模块拆解定案

日期：2026-06-05

## 1. 定案目标

这份定案只解决三件事：

1. 一个后台、两个前端长期怎么共存
2. `530.1` 里的模块应该拆到 `ygb`、`azb` 还是双视图共享
3. `6.1` 评分体系如何挂回现有模块，而不是再做第三套页面

当前仓库边界已经明确：

- 后端继续一套业务域、一套主数据、一套权限底座
- 前端固定两套门户
  - `yuegongbao-ui/src/views/ygb`
  - `yuegongbao-ui/src/views/azb`
- 登录页已双入口化
  - `/login/ygb`
  - `/login/azb`
- 路由已经具备门户分流基础
  - `yuegongbao-ui/src/router/index.js`

## 2. 先把“七成共性”说清楚

“七成内容一样”在工程上只能解释为下面三类共性：

### 2.1 数据共性

必须共后台的数据对象：

- 企业
- 人员
- 设备
- 预警
- 高处作业
- 工伤事件
- 安责险保单
- 事故预防资金
- 事故预防项目
- AI 报告与 AI 配置
- 信用评价
- 统计报表底数

### 2.2 业务内核共性

原则上只保留一套的能力：

- CRUD
- 状态机
- 上传下载
- 导入导出
- 字典
- 角色权限
- 第三方对接与 Stub

### 2.3 页面表达差异

这一层不能按“共性”处理，必须分门户：

- 登录页
- 首页工作台
- 菜单树
- 模块说明
- 摘要卡
- 默认筛选
- 焦点队列
- 详情抽屉重点
- 快捷入口
- 推荐动作按钮

结论：

- `70% 共性 = 共后台 + 共数据 + 共内核`
- 不等于 `70% 页面继续共用`

## 3. 两个门户的长期定位

### 3.1 `ygb`

`ygb` 长期固定为：

- 企业办理工作台
- 人社监管工作台
- 财务整改工作台

页面关键词固定为：

- 办理
- 补录
- 对账
- 整改
- 归档
- 闭环

### 3.2 `azb`

`azb` 长期固定为：

- 应急治理工作台
- 安责险协同工作台
- 风险处置工作台

页面关键词固定为：

- 风险
- 治理
- 处置
- 时效
- 在途
- 重点对象

## 4. 模块是否必须双视图的判定规则

任意模块上线前，先看下面 6 条：

1. 主要使用角色是否不同
2. 首要动作是否不同
3. 首页入口优先级是否不同
4. 详情页关注重点是否不同
5. 摘要卡与焦点队列是否不同
6. 按钮密度和操作深度是否不同

命中任意 2 条：

- 走 `共后台 + 双前端双视图`

只命中 0 到 1 条：

- 才允许继续共页面或轻包装

### 5.3 `azb` 主责表达模块

从底层对象看，它们还是共享对象；但从门户表达上，以下页面以后应优先按 `azb` 口径演进：

- `views/azb/cockpit`
- `views/azb/device`
- `views/azb/warning`
- `views/azb/heightWorkReport`
- `views/azb/aqInsurance`
- `views/azb/aiReport`
- `views/azb/creditScore`

原因不是要复制后台，而是这些模块在应急侧的“首要动作、摘要重点、详情重点、队列优先级”已经明显不同。

## 6. 两个监管部门重叠内容怎么拆

“重叠很多”不等于“同一页继续兼容”。

固定拆法：

### 6.1 同对象，不同入口

典型模块：

- 单位管理
- 人员管理
- 预警中心
- 工伤事件
- 高处作业
- AI 报告
- 统计报表

统一处理方式：

- 后台共一套对象
- `ygb` 从办理链进入
- `azb` 从风险对象进入

### 6.2 同数据，不同动作

以高处作业为例：

- `ygb`
  - 先看是否已报备
  - 是否能结束登记
  - 是否缺少完成照片
- `azb`
  - 先看进行中高危作业
  - 是否证书异常
  - 是否超时未结束
  - 是否处于重点区域

以设备管理为例：

- `ygb`
  - 先看接入授权
  - 先看在线回写是否异常
- `azb`
  - 先看离线
  - 先看锁机失败
  - 先看围栏越界
  - 先看拆除报警

以预警中心为例：

- `ygb`
  - 先看工资、社保、合同、高处作业关联待办
- `azb`
  - 先看红警、重大隐患、重复预警、超时处置

## 7. 6.1 评分体系挂接定案

### 7.1 `ygb` 的评分解释主链

| 评分域 | 对应模块 | 页面解释重点 |
| --- | --- | --- |
| A 工伤预防 | 工伤事件、预防项目、预防资金、统计报表 | 发生率、认定及时率、基金效益 |
| B 用工合规 | 合同、考勤、工资、社保、个税、用工比例、假外包 | 异常对象、整改闭环、财务对账 |
| C 设备安全 | 设备、预警、工伤 | 与用工安全相关的授权和事故压降 |
| D 参保扩面 | 社保、安责险、漏保清单 | 催缴完成率、补缴率、覆盖率 |
| E 预警处置 | 预警中心、AI 报告、规则 | 待办量、逾期量、闭环效率 |
| F 技术防范 | 高处作业、设备、AI 报告 | 报备留痕、识别违规、现场佐证 |

### 7.2 `azb` 的评分解释主链

| 评分域 | 对应模块 | 页面解释重点 |
| --- | --- | --- |
| AQ 安责险合规 | 安责险、预防资金、预防项目 | 投保覆盖、保额达标、资金健康 |
| C 设备安全 | 设备、预警、工伤 | 在线率、离线时长、锁机成功率 |
| F 技术防范 | 高处作业、AI 报告、设备 | 高危作业在途风险、识别准确率、压降趋势 |
| H 隐患整改 | 预警中心、AI 报告、设备 | 重大隐患整改率、重复隐患率、逾期率 |
| E 预警处置 | 预警中心、驾驶舱、统计报表 | 响应时效、升级率、未闭环致事故率 |

### 7.3 固定规则

1. 同一企业在 `ygb`、`azb` 共用一份底数
2. 同一底数在两个门户必须输出不同解释
3. 权重与得分点不能写死在页面里，应走配置和聚合层

## 8. 面向当前仓库的直接实施要求

### 8.1 前端目录要求

- `views/ygb/*`
  - 只承接企业办理、人社监管、财务整改主语义
- `views/azb/*`
  - 只承接应急治理、安责险协同、风险处置主语义

### 8.2 后端接口要求

共享模块统一遵循：

- 业务 CRUD 不复制两套
- 增补门户聚合接口
  - `summary`
  - `dashboard`
  - `detail hint`

### 8.3 页面结构要求

`ygb` 高频页统一结构：

1. 业务定位
2. 摘要卡
3. 办理焦点
4. 当前选中对象
5. 推荐办理动作
6. 搜索区
7. 工具栏
8. 表格
9. 详情抽屉

`azb` 高频页统一结构：

1. 治理定位
2. 摘要卡
3. 风险队列
4. 当前风险对象
5. 推荐处置动作
6. 风险提示标签
7. 搜索区
8. 工具栏
9. 治理台账
10. 详情抽屉

## 9. 最终定案

1. 当前仓库适合继续走“一套后台、两个前端门户”路线，不应再回到“单页兼容双监管语义”。
2. `530.1` 里的大部分主数据与主流程继续共后台，但页面表达必须按 `ygb`、`azb` 分流。
3. `6.1` 评分体系不应单独再生一套前端，而应挂回现有共享模块，形成“双门户、双解释口径”。
4. 后续所有新模块立项前，先判断它是 `ygb` 独占、`azb` 主责，还是双视图共享模块，再进入开发。
