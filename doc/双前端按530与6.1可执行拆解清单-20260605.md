# 双前端按 530.1 与 6.1 可执行拆解清单

## 1. 这份清单解决什么问题

这份清单不再讨论“双前端要不要做”，只固定三件事：

1. 一个后台、两个前端到底怎么长期共存
2. `530.1` 业务模块按什么规则拆到 `ygb` 和 `azb`
3. `6.1` 评分体系怎样回挂到双门户，而不是再做一套重复页面

适用边界固定为：

- 后端保持一套业务域、一套主数据、一套状态机
- 前端固定为 `粤工保（ygb）` 与 `安责保（azb）` 两个门户
- 登录页、首页、菜单、驾驶舱、详情重点允许双前端差异
- 企业、人员、设备、预警、高处作业、AI、工伤、安责险等底座继续共后台

## 2. 固定结论

### 2.1 “七成共性”在工程上的真实含义

“七成共性”应固定解释为：

- 共数据
- 共业务内核
- 共接口主链
- 共组件能力

不能再解释为：

- 七成页面继续共用
- 一个页面同时承接两种监管语义
- 只换登录页和 Logo 就算双前端

### 2.2 双门户长期定位

`ygb` 固定定位为：

- 企业办理工作台
- 人社监管工作台
- 财务整改工作台

`azb` 固定定位为：

- 应急治理工作台
- 安责险协同工作台
- 风险处置工作台

### 2.3 模块是否必须双视图的判定规则

一个模块命中下列任意 2 条，就必须走 `共后台 + 双前端双视图`：

1. 主要使用角色不同
2. 首要动作不同
3. 首页入口优先级不同
4. 详情页关注重点不同
5. 默认摘要卡和焦点队列不同
6. 按钮密度和操作深度不同

5. `azb` 不承接企业劳务办理主链

## 5. 按 6.1 的评分挂接定案

### 5.1 `ygb` 评分解释主链

| 评分解释域 | 主承接模块 | 页面解释重点 |
| --- | --- | --- |
| 工伤预防 | 工伤事件、预防项目、预防资金、统计报表 | 看发生率、整改率、归档率 |
| 用工合规 | 合同、考勤、工资、社保、个税、用工比例、假外包 | 看异常对象、整改闭环、财务对账 |
| 扩面减损 | 社保、安责险、漏保清单 | 看催缴完成率、补缴完成率、覆盖率 |
| 预警处置 | 预警中心、规则、AI 报告 | 看待办量、逾期量、闭环效率 |
| 技术防范 | 高处作业、设备、AI 报告 | 看报备留痕、异常压降、现场佐证 |

### 5.2 `azb` 评分解释主链

| 评分解释域 | 主承接模块 | 页面解释重点 |
| --- | --- | --- |
| 安责险合规 | 安责险、预防资金、预防项目 | 看投保覆盖、资金健康、服务执行 |
| 设备安全 | 设备、预警、工伤事件 | 看在线率、离线时长、处置时效 |
| 技术防范 | 高处作业、AI 报告、设备 | 看在途高危作业、识别异常、压降趋势 |
| 隐患整改 | 预警中心、AI 报告、设备 | 看重大隐患、重复隐患、超时未闭环 |
| 应急响应 | 驾驶舱、统计报表、区域队列 | 看区域态势、重点对象、处置时效 |

### 5.3 固定口径

1. 同一企业在 `ygb` 和 `azb` 可以共用同一底数
2. 同一底数在两个门户必须输出不同解释
3. 评分调整优先通过配置完成，不再写死在页面

## 6. 当前仓库的直接落地要求

按现有代码和目录，后续开发固定遵循：

- `yuegongbao-ui/src/views/ygb/*`
  - 承接企业办理、人社监管、财务整改主链
- `yuegongbao-ui/src/views/azb/*`
  - 承接应急治理、安责险协同、风险处置主链
- 后端继续只保留一套业务域
  - 通过 `summary/dashboard/detail` 做门户差异聚合

当前代码已具备的底座事实：

1. 两个登录入口已存在
2. 首页工作台已按门户分流
3. `portal_scope`、`allowed_portal_scope`、`default_portal_code` 已接入
4. `views/ygb` 与 `views/azb` 双目录已形成
5. 只读角色轻视图工具已存在

所以后续重点不再是“要不要拆”，而是“每个共享模块如何做双语义落地”。

## 7. 新模块立项时必须先回答的 8 个问题

1. 这是 `ygb` 独占、`azb` 主责，还是双视图共享模块
2. 主数据是否继续共后台
3. 是否需要 `summary/dashboard` 聚合接口
4. `ygb` 和 `azb` 的默认入口是否不同
5. 两个门户的详情重点是否不同
6. `108/109` 是否需要轻视图
7. 它挂到 `6.1` 的哪个评分解释域
8. 首页是否要放快捷入口或焦点队列

这 8 个问题没答清楚，就不应该直接进入页面开发。

## 8. 最终定案

1. 一个后台两个前端是正确方向，而且当前仓库已经具备持续推进的基础。
2. `70% 共性` 只说明共后台成立，不说明共页面成立。
3. 人社与应急的大量重叠内容，应统一落成“同对象、双入口、双摘要、双详情重点”。
4. 后续产品排期、前端派工、后端补接口、测试验收，都先以这份清单判断模块归属。
