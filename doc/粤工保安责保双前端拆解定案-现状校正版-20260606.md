# 粤工保安责保双前端拆解定案（现状校正版）

日期：2026-06-06

## 1. 定案结论

当前系统应固定为：

- 一套后台
- 两个前端门户：`ygb`、`azb`
- 两套登录页、两套首页工作台、两套路由壳和菜单显隐
- 一套企业/人员/预警/设备/高处作业/工伤/安责险/AI/统计等核心业务底座

这不是“一个后台换两套标题”，而是：

- `ygb` 承接 530.1 主业务链，偏企业办理、财务对账、人社监管、整改闭环
- `azb` 承接 6.1 监管解释链，偏应急监管、安责险协同、设备安全、风险治理
- 两端共享同一批业务对象和核心接口，但页面组织、首页入口、详情摘要、指标解释、推荐动作必须分开

## 3. 总体架构定案

### 3.1 后台必须共用的边界

以下对象必须保持单源，不允许为 `azb` 再复制第二套业务表和第二套业务接口：

- 企业
- 人员
- 角色、菜单、权限
- 预警、预警规则
- 设备
- 高处作业申报报备
- 工伤事件
- 安责险保单
- 事故预防项目、事故预防资金
- AI 原始事件、AI 报告、AI 配置
- 信用评分底座
- 统计报表底座

共享后台的正确含义是：

- 一套表结构
- 一套主状态机
- 一套核心接口
- 一套导入导出主逻辑
- 一套统一字典、上传、附件、审计和权限底座

共享后台不等于：

- 共用同一套首页
- 共用同一套工作台摘要
- 共用同一套详情页重点字段
- 共用同一套评分解释文案

### 3.2 前端必须拆开的边界

前端按门户拆开的内容必须包括：

- 登录页品牌
- 首页工作台
- 驾驶舱摘要
- 菜单树和默认入口
- 详情页高亮信息
- 指标口径说明
- 待办推荐动作

统一技术模式固定为：

- 共享逻辑层：`src/views/<module>/useXxxPage.js`
- 粤工保壳层：`src/views/ygb/<module>/index.vue`
- 安责保壳层：`src/views/azb/<module>/index.vue`

## 4. 模块拆解定案

### 4.1 只在 `ygb` 完整承载的办理链模块

这些模块属于企业办理、财务对账、人社合规主链，不建议在 `azb` 再做完整录入办理页：

- `contract`
- `attendanceRaw`
- `attendanceMonthly`
- `salaryBatch`
- `salaryDetail`
- `socialPayment`
- `socialBaseCompare`
- `taxCompare`
- `employmentRatio`
- `fakeOutsourcing`
- `newformWorker`
- `occupationMonitor`

原则：

- `azb` 如需消费这些数据，只允许引用摘要结果、风险结论、评分解释
- `azb` 不再承接这些模块的完整原始办理流程

### 4.2 共后台 + 双前端壳层的共享模块

这 16 个模块必须坚持“共享逻辑、双壳表达”：

- `aiReport`
- `aiReportConfig`
- `aqInsurance`
- `cockpit`
- `creditScore`
- `device`
- `enterprise`
- `heightWorkReport`
- `injuryEvent`
- `person`
- `preventionFund`
- `preventionProject`
- `statReport`
- `uninsuredList`
- `warning`
- `warningRule`

拆分要求：

- `ygb` 看办理、整改、对账、归档
- `azb` 看风险、处置、时效、在途、区域治理
- 同一对象在两端都可查询，但首页入口、字段排序、详情摘要、推荐动作不能相同

### 4.3 `azb` 的主责强化模块

虽然底座共享，但以下模块在 `azb` 必须明显比 `ygb` 更强表达：

- `aqInsurance`
- `device`
- `warning`
- `heightWorkReport`
- `aiReport`
- `creditScore`
- `statReport`
- `preventionFund`
- `preventionProject`
- `injuryEvent`

`azb` 首屏应优先强调：

- 当前风险等级
- 区域热区
- 在途处置
- 超时未闭环
- 重点对象队列
- 下一步治理动作

### 4.4 `ygb` 的主责强化模块

`ygb` 必须保持第一优先级的业务链：

- 合同备案
- 考勤采集与归集
- 工资批次与工资明细
- 社保缴费与基数比对
- 税务比对
- 预警整改
- 扩面减损
- 高处作业企业报备闭环

`ygb` 首屏应优先强调：

- 当前待办
- 办理堵点
- 回写状态
- 月度归档节点
- 企业高频入口
- 财务高频入口

## 5. 角色与门户归属

门户默认归属应固定为：

| 角色 | 默认门户 | 长期定位 |
| --- | --- | --- |
| `104 ygb_enterprise_admin` | `ygb` | 企业管理员 |
| `105 ygb_enterprise_operator` | `ygb` | 企业经办员/操作员 |
| `106 ygb_hrss_supervisor` | `ygb` | 人社监管员 |
| `107 ygb_emergency_supervisor` | `azb` | 应急监管员 |
| `108 ygb_insurer` | `azb` | 保险公司 |
| `109 ygb_bank` | `azb` | 银行 |

固定规则：

1. `104/105/106` 默认进入 `ygb`
2. `107/108/109` 默认进入 `azb`
3. 企业角色允许访问双门户，但从 `azb` 进入后必须切换成“现场治理视角”
4. 保险、银行角色保持轻视图和只读视图，不暴露完整录入和整改动作

## 6. 530.1 与 6.1 的挂接口径

### 6.1 530.1 对应 `ygb`

530.1 的主价值链应主要落在 `ygb`：

- 劳务合规
- 工资发放
- 社保税务比对
- 用工比例与假外包治理
- 工伤预防
- 扩面减损

### 6.2 6.1 对应 `azb`

6.1 的主解释链应主要落在 `azb`：

- 安责险覆盖
- 设备安全
- 技术防范
- AI 风险识别
- 隐患整改
- 区域治理成效

### 6.3 评分与解释的实现原则

固定原则：

1. 同一企业在 `ygb` 与 `azb` 共用同一底数
2. 两端只改变解释顺序、摘要视角和推荐动作
3. 权重、阈值、得分点必须配置化，不允许写死在页面
4. AI 报告、统计报表、驾驶舱允许按门户输出不同解释口径

## 7. 对研发的直接要求

后续所有双前端改造统一按以下口径执行：

1. 后台坚持单套对象、单套状态机、单套核心接口
2. 门户差异优先落在前端壳层，不回退成后台双分支
3. 共性模块统一走“共享逻辑 + 双壳”
4. 企业办理主链收口到 `ygb`
5. 风险治理主链强化到 `azb`
6. 同一对象允许双视图，不允许双建模

## 8. 这份文档的用途

这份文档用于统一：

- 产品拆解边界
- 模块归属
- 双前端承载范围
- 后台单源边界
- 角色与门户归属
- 后续研发、联调、验收口径
