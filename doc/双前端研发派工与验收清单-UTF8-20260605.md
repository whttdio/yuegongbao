# 双前端研发派工与验收清单

日期：2026-06-05

## 1. 目标

这份清单直接用于产品、前端、后端、测试排期，目标不是继续讨论方案，而是明确：

1. 先做什么。
2. 谁来做。
3. 每批产出什么。
4. 怎么验收。

## 2. 当前基线

当前仓库已具备继续落地双前端的基础：

1. 双登录入口已存在。
2. `ygb` 与 `azb` 视图目录已拆开。
3. 后端已接入 `portal_scope`、角色默认门户、角色可访问门户控制。
4. 菜单与角色 SQL 已进入分阶段脚本管理。
5. 部分 `azb` 页面已从通用 CRUD 升级为工作台化页面。

当前最缺的不是底座，而是：

1. 模块归属与双视图边界统一口径。
2. 共享模块持续按角色视角改造。
3. 530.1 与 6.1 的数据解释挂接。
4. 派工和验收标准统一。

## 3. 批次规划

### P0：双门户边界与角色归位

目标：

- 先把“谁进哪个门户、哪些模块属于谁”收口。

产出：

1. 角色默认门户、允许门户范围核对完毕。
2. 菜单 `portal_scope` 全量核对。
3. `ygb`、`azb` 首页入口不再混乱。

派工：

| 角色 | 工作项 |
| --- | --- |
| 产品 | 确认模块归属矩阵、角色归位矩阵 |
| 后端 | 核对 `sys_role`、`sys_menu`、`sys_role_menu` 门户字段与查询逻辑 |
| 前端 | 核对登录后默认跳转、菜单渲染、路由兜底 |
| 测试 | 覆盖 104/105/106/107/108/109 的门户进入与菜单显隐 |

验收：

1. `104/105/106` 登录默认进入 `ygb`。
2. `107/108/109` 登录默认进入 `azb`。
3. `108/109` 不出现重维护类按钮。
4. 非授权门户不能通过地址直接绕过进入。

### P1：首页与驾驶舱工作台化

目标：

- 把双门户首页真正做成高频工作入口，而不是大号菜单页。

产出：

1. `ygb` 首页承接企业办理、人社监管、财务整改。
2. `azb` 首页承接应急治理、安责险协同、只读协同下钻。
3. 驾驶舱与首页职责分离。

派工：

| 角色 | 工作项 |
| --- | --- |
| 产品 | 定义各角色首页焦点顺序、摘要卡、推荐入口 |
| 前端 `ygb` | `ygb/cockpit`、`views/index.vue`、相关摘要组件联动 |
| 前端 `azb` | `azb/cockpit`、门户首页聚合组件联动 |
| 后端 | 补齐首页 `summary/dashboard` 聚合接口 |
| 测试 | 验证不同角色首页焦点顺序、卡片、默认对象是否不同 |

验收：

1. 企业管理员首页优先出现办理闭环。
2. 企业经办员首页优先出现录入、修改、结束登记。
3. 人社监管员首页优先出现区域异常与闭环报表。
4. 应急监管员首页优先出现红警、设备、高危作业、AI 风险。
5. 只读角色首页只出现摘要、详情、导出入口。

### P2：共享模块双视图改造

目标：

- 把共用模块从“同表不同菜单”升级成“同对象双语义工作台”。

优先级顺序：

1. 预警中心
2. 设备管理
3. 高处作业申报报备
4. 安责险管理
5. 事故预防资金池
6. 事故预防项目
7. 工伤事件
8. AI 监测报告
9. AI 模型配置
10. 信用评价
11. 统计报表
12. 漏保清单
13. 单位管理
14. 人员管理

每个模块必须完成的前端动作：

1. 顶部定位文案区分 `ygb` 与 `azb`。
2. 摘要卡按门户角色重排。
3. 提供焦点队列或办理焦点。
4. 提供当前对象推荐面板。
5. 提供动态主动作按钮。
6. 表格支持焦点优先排序。
7. 详情页补治理提示标签。

每个模块必须完成的后端动作：

1. 保持统一主数据和主接口。
2. 补齐 `summary` 聚合数据。
3. 如需首页承接，再补 `dashboard` 聚合数据。
4. 如需详情差异表达，再补详情聚合字段，不复制业务表。

验收：

1. 同一对象在 `ygb` 与 `azb` 中打开，页面关注重点不同。
2. `ygb` 页面默认动作是办理、补录、结束、归档。
3. `azb` 页面默认动作是查看详情、处置、追踪、协同。
4. 只读角色仅保留摘要、详情、导出。

### P3：530.1 底数接入 6.1 评分解释

目标：

- 同一批业务底数，在两个门户输出不同评分解释。

后端工作项：

1. 建立评分维度、得分点、权重、目标值配置。
2. 聚合合同、考勤、工资、社保、安责险、设备、预警、高处作业、工伤、AI 等底数。
3. 输出企业分、区域分、维度分、得分点明细。
4. 为 AI 报告、信用评价、统计报表提供统一评分结果引用。

前端工作项：

1. `ygb` 把评分解释落到工伤预防、用工合规、参保扩面、预警闭环、技术防范。
2. `azb` 把评分解释落到安责险合规、设备安全、技术防范、隐患整改、应急响应。
3. 同一企业在双门户显示不同的解释顺序、摘要重点、推荐动作。

验收：

1. 同一企业在 `ygb` 与 `azb` 中看到的评分解释不同。
2. 每个得分点都能追溯到具体对象或聚合指标。
3. 权重调整不需要改页面逻辑。

### P4：SQL、权限、验收总收口

目标：

- 统一 SQL、权限、菜单、测试标准。

后端/实施工作项：

1. 核对 `ygb_phase8` 至 `ygb_phase11` 相关 SQL。
2. 统一角色、菜单、按钮权限注入。
3. 所有共享模块补齐 `portal_scope`。
4. 核对只读角色权限兜底。

测试工作项：

1. 菜单显隐。
2. 按钮显隐。
3. 接口权限拦截。
4. 角色跨门户跳转兜底。
5. SQL 幂等执行。

验收：

1. 菜单可见性与角色矩阵一致。
2. 按钮权限与后端权限一致。
3. SQL 重复执行无重复角色、菜单、关系数据。
4. 双门户构建均通过。

## 4. 具体分工

### 4.1 产品分工

产品必须给清楚以下内容，否则不进入编码：

1. 模块归属：`ygb` 独占、`azb` 主责、还是双视图共享。
2. 角色优先级：谁先看、谁先办、谁只读。
3. 焦点队列：每个角色进入后最先关注什么。
4. 推荐动作：进入页面后主按钮应该是什么。
5. 评分解释：同一模块在双门户各自解释什么。

### 4.2 后端分工

后端只做一套业务底座，但必须补齐门户聚合层：

1. 统一主表与明细表。
2. 统一 CRUD。
3. 统一导入导出。
4. 补 `summary`。
5. 补 `dashboard`。
6. 补详情聚合字段。
7. 补角色门户兜底。
8. 补只读权限兜底。

### 4.3 前端分工

前端必须按双视图目录持续建设：

1. `src/views/ygb/*` 只承接企业办理、人社监管、财务整改语义。
2. `src/views/azb/*` 只承接风险治理、安责险协同、只读协同语义。
3. 不再把共享模块做成同一页面简单复制。
4. 统一工作台结构，不再停留在基础 CRUD。

### 4.4 测试分工

测试必须按“角色 + 门户 + 模块 + 动作”四维验收：

1. 角色进入哪个门户。
2. 门户能看到哪些模块。
3. 模块里能做哪些动作。
4. 同对象在双门户里看到的重点是否不同。

## 5. 每个共享模块的标准交付模板

每做一个共享模块，都必须交付以下内容：

1. 模块归属说明。
2. `ygb` 页面语义。
3. `azb` 页面语义。
4. 角色差异。
5. 聚合接口字段。
6. 焦点队列定义。
7. 推荐动作定义。
8. 详情提示标签定义。
9. 菜单权限定义。
10. 验收用例。

## 6. 标准验收用例

每个模块至少通过以下验收：

1. 企业管理员可完成新增、编辑、结束、导出等企业动作。
2. 企业经办员只能做缩减版企业动作。
3. 人社监管员只看到监管侧需要的查看和督办入口。
4. 应急监管员看到的是风险与时效优先的台账。
5. 保险、银行角色只看到只读视图。
6. 同一对象在 `ygb` 和 `azb` 的详情重点不相同。
7. 无权限按钮即使前端隐藏，后端也会拦截。

## 7. 风险与约束

当前推进中最需要控制的风险：

1. 误把“共后台”做成“共页面”。
2. 评分解释直接写死在前端。
3. 只做菜单显隐，不做接口权限兜底。
4. 首页做成装饰面板，不承接真实高频动作。
5. 在脏工作区内大面积改文件而不做批次收口。

控制措施：

1. 每批只收口一类问题。
2. 共享模块统一按工作台模板升级。
3. 评分解释走配置与聚合，不走页面硬编码。
4. 每批都要有构建验证与角色验收。

## 8. 交付定义

一个批次只有同时满足以下条件才算完成：

1. 文档归属与角色口径已确认。
2. SQL/权限已注入或已给出可执行脚本。
3. 前端页面已完成双视图表达。
4. 后端聚合接口已补齐。
5. 构建通过。
6. 角色验收通过。
7. 测试用例有结果。

## 9. 建议的下一步

按当前仓库状态，建议下一步固定顺序：

1. 先用本清单收口角色与模块归属。
2. 再持续完成剩余共享模块的工作台化改造。
3. 同步启动 6.1 评分聚合接口设计。
4. 最后统一做权限、SQL 与全链路验收。
