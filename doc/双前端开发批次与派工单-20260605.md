# 双前端开发批次与派工单

## 1. 用途

这份文档直接服务研发、产品、测试排期，不再讲双前端要不要做，只回答四件事：

- 先做什么
- 后端补什么
- 前端改什么
- 验收怎么过

执行前提固定为：

- 后台保持一套
- 前端固定为 `ygb` 和 `azb` 两套工作台
- 共享模块优先补 `summary/dashboard`
- 不再接受“一个页面兼顾两种门户语义”的长期方案

## 2. 派工总原则

### 2.1 后端原则

- 不复制两套 CRUD
- 先补聚合接口，再改页面
- 同对象按门户拆 `summary/dashboard`
- 敏感动作继续由后端权限兜底
- 评分、首页、驾驶舱允许门户级解释差异

### 2.2 前端原则

- `ygb` 统一按办理台账组织
- `azb` 统一按治理工作台组织
- 只读角色先在前端显式收口
- 行点击、当前对象、详情抽屉必须联动
- 首页、详情、按钮密度必须体现角色差异

### 2.3 优先级原则

优先顺序固定为：

1. 高频主链
2. 首页与角色默认入口
3. 评分维度映射
4. 低频配置页和辅助页

## 3. 当前底座状态

当前仓库已经具备继续推进双前端的必要基础，不需要再回到框架层争论：

- 两个登录入口已落地
- `X-Portal-Code` 已接入
- `sys_menu.portal_scope` 已接入
- 角色已支持 `allowed_portal_scope` 和 `default_portal_code`
- 路由和门户品牌切换已具备
- `views/ygb` 与 `views/azb` 已形成双视图目录结构
- 只读角色轻视图工具已存在

因此后续重点只剩三类：

- 剩余高频页工作台化
- 门户聚合和评分口径化
- 角色、菜单、按钮与目标库一致性收口

## 4. 批次总览

| 批次 | 目标 | 主要门户 | 主要对象 | 结果要求 |
| --- | --- | --- | --- | --- |
| P0 | 补齐 `ygb` 剩余高频主链工作台 | `ygb` | 财务整改、专项合规、企业办理 | 企业管理员、操作员、财务能闭环高频办理 |
| P1 | 强化 `azb` 多角色治理工作台 | `azb` | 驾驶舱、预警、设备、高处作业、安责险、AI | 应急、保险、银行看到不同入口和摘要 |

| P3 | 收口 SQL、角色、菜单、按钮和验收脚本 | 双端 | 门户归属、角色授权、轻视图、首页入口 | 权限与页面显隐完全一致 |

把仍然偏基础 CRUD 的 `ygb` 页面升级成企业管理员、操作员、财务能长期高频使用的办理台账。

### 5.2 页面范围

| `ygb/employmentRatio` | 已完成工作台化 | 继续在首页和评分链中承接合规对象 |
| `ygb/fakeOutsourcing` | 已完成工作台化 | 继续在专项治理链和预警链中承接疑似对象 |
| `ygb/newformWorker` | 已完成监管台账化 | 继续补首页重点对象联动 |
| `ygb/occupationMonitor` | 已完成监管台账化 | 继续补区域异常联动 |
| `ygb/cockpit` | 已工作台化 | 继续补首页协同和角色默认入口 |

| 模块 | 接口动作 |
| --- | --- |
| 个税比对 | 补 `GET /ygb/tax/compare/summary`，返回总量、异常量、待整改、重点对象 |

| 职业病监测 | 若摘要不足，补区域/行业异常聚合 |
| 首页工作台 | 继续补财务链、整改链、监管链聚合队列 |

### 5.4 前端派工

`ygb` 高频页统一按下面结构实施：

1. 顶部业务定位
2. 摘要卡
3. 办理承接焦点
4. 当前选中对象
5. 办理路径
6. 搜索区
7. 工具栏
8. 台账表格
9. 详情抽屉

### 5.5 P0 验收

1. 企业管理员进入页面后 3 秒内知道先办什么
2. 财务进入页面后直接看到异常原因、整改对象、导出入口
3. 摘要来自后端聚合，不从当前页临时计算
4. 构建通过 `vite build --mode ygb`

## 7. P2：评分体系接入批

### 7.1 目标

把 `530.1` 的业务底数正式转换成 `6.1` 的评分维度，不再停留在静态台账或口头分析。

### 7.2 后端派工

| 类型 | 派工内容 |
| --- | --- |
| 评分配置 | 新增或复用评分配置表，支持维度、得分点、权重、目标值 |
| 数据聚合 | 按月聚合工伤、安责险、设备、预警、技术防范、合规整改指标 |
| 评分计算 | 输出企业分、区域分、维度分、明细得分点 |
| 结果存储 | 保存历史评分结果，供 AI 报告、统计报表、信用评价引用 |

### 7.3 前端派工

| 门户 | 派工内容 |
| --- | --- |
| `ygb` | 首页、统计报表、AI 报告突出工伤预防、用工合规、扩面减损、预警闭环 |
| `azb` | 首页、统计报表、AI 报告突出安责险合规、设备安全、技术防范、隐患整改、应急响应 |

### 7.4 P2 验收

1. 同一企业在 `ygb` 和 `azb` 能看到不同评分解释
2. 每个维度能追溯到具体业务模块
3. 权重调整通过配置完成，不需要改核心代码

## 8. P3：SQL、菜单、角色矩阵收口批

### 8.1 目标

把页面、角色、菜单、按钮、目标库数据完全对齐，避免前端能看到但后端无权，或 SQL 已注入但门户归属错误。

### 8.2 SQL 派工

固定围绕以下字段核对：

- `sys_menu.portal_scope`
- `sys_role.allowed_portal_scope`
- `sys_role.default_portal_code`
- `sys_role_menu.portal_scope`

重点核对清单：

1. `ygb` 独占模块是否全部收口到 `portal_scope=ygb`
2. 双门户共享模块是否正确标记为 `both`
3. `107/108/109` 是否默认归位 `azb`
4. `108/109` 是否只保留查询、详情、导出类权限
5. 高处作业、设备、安责险、AI、预警等共享模块按钮是否按门户收口

### 8.3 前端派工

| 范围 | 动作 |
| --- | --- |
| 只读轻视图 | 统一复核 `roleView` 收口是否覆盖全部高频页 |
| 首页入口 | 检查 `ygb` 与 `azb` 快捷入口是否完全分流 |
| 菜单显隐 | 检查共享模块是否正确落在 `views/ygb` 或 `views/azb` |
| 详情语义 | 检查同对象在双门户详情重点是否分开 |
| 登录归位 | 检查角色跨门户自动归位是否符合矩阵 |

### 8.4 P3 验收

1. 菜单显隐与目标库授权完全一致
2. 只读角色前后端双重收口一致
3. 同一账号切换门户后，首页、菜单、按钮、详情重点都变

## 10. 当前最合理的推进顺序

如果按你现在的业务优先级和当前代码现状，建议固定为：

1. `ygb/cockpit` 首页角色入口和重点对象联动
2. `azb/cockpit` 角色队列继续细化
3. `azb/device` 现场负责人和设备管理员轻重视图继续细化
4. `azb/heightWorkReport` 在途作业、凭证和结束佐证继续细化
5. `azb/injuryEvent` 继续补事故协同字段和治理摘要
6. 评分体系接入
7. SQL/角色矩阵总核对

原因很直接：

- 当前 80% 主需求仍在 `ygb`
- 企业高频问题先暴露在财务整改链和办理主链
- `azb` 底座已经成型，更适合下一步做角色细分与评分深化

## 11. 最终结论

1. 继续坚持一套后台，不新拆第二套业务库。
2. 页面层面必须长期维持两个前端工作台。
3. 共性高，不代表页面继续共用。
4. 后续所有任务都先按这份批次单派工，再进入代码开发。
